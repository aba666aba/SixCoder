# 22 · 三档模式的**协作方式**（不是权限）

`docs/19` 讲的是"能做什么"（权限：能不能写文件、能不能调远端）。这一份讲**谁拍板、谁写代码**——
两档模式的差别主要在这里，权限只是表面。

## 一、先把上限说清楚

| | 甲方模式 | 开发者模式 | 只读模式 |
|---|---|---|---|
| 本质 | 写代码的**完全体** | **工具** | 只读的分析器 |
| 上限来自 | **远端 API 的推理能力** | **开发者本人的架构能力** | 人的判断 |
| 谁拍板 | 远端 API | 开发者 | 开发者 |
| 谁决定架构 | 系统内部自己定 | 必须由人给出方案 | 不涉及 |
| 系统做什么 | 需求 → 内部做完所有决策 → 交付报告 | 照人给的方案实现，机械验证 | 读懂、审查、给建议 |
| 本地小模型 | 便宜工人（可机械验证的活） | 打字机（照方案写） | 不写 |

一句话：
- **甲方模式**要求"远端和本地协调完美完成任务"，任何问题都由远端做最终裁判；
- **开发者模式**要求"人、本地、远端三部分按人的方案协同"，系统不许替人做架构决策。

## 二、落成代码：三个策略位

`core/policy.py`：

| 策略位 | 含义 | 甲方模式 | 开发者模式 | 只读 |
|---|---|---|---|---|
| `arbiter` | 谁做最终裁判 | `remote` | `human` | `human` |
| `code_escalation` | 什么时候把写代码交给远端 | `first-red` | `on-approval` | `off` |
| `plan_authority` | 实现方案的权威 | `remote` | `human` | `human` |
| `remote_code_budget` | 整夜远端接管写代码的上限 | 200 次 | 0（不自动接管） | 0 |

具体行为：

1. **甲方模式**：本地被**硬判据**判红（签名/边界/契约/SQL/回归）就**立刻**把这张单交给远端写代码，
   不再等"连续失败 2 次"——本地小模型做不出来的东西，多试只是烧时间。
   软失败（没吐 JSON、超时）仍先本地重试。整夜有次数上限，超了就不再接管（并写进报告）。
2. **开发者模式**：远端接管仍按"连续失败 2 次 + 人工批准"走；`remote.call` 本来就是关键节点。
   需要架构决策但没有 `plan` 时，抛 `needhuman` 停下问人，这一轮只做机械派工。
3. **只读模式**：直接拒绝跑夜班（不写任何文件）。

## 三、甲方模式的入口（以前只有 Python 脚本，现在能直接跑）

```powershell
# 命令行：提需求 → 夜里自动跑 → 早上看 DELIVERY.md
python cli.py night --repo E:\path\to\repo --requirement-file 需求.txt --hours 6
```

```http
POST /v1/night   {"repo": "...", "requirement": "...", "hours": 6}
GET  /v1/night   → 所有夜班状态
GET  /v1/night/{task_id} → 进展 + 交付报告正文
GET  /v1/tasks/{task_id}/stream → 复用现有 SSE 看实时进度
```

交付报告里新增「协作方式」一节：这一夜是谁在拍板、远端接管了几次、方案是不是人给的。
甲方早上只看这一份，不用读代码。

## 四、开发者模式：方案（plan）是权威

```powershell
python cli.py night --repo ... --requirement-file 需求.txt --plan-file 方案.md
```

方案会原样进入**执行者**与**架构师**的提示词，并带三条硬约束：

```
【实现方案（开发者（你只能照它做）给的，必须照做）】
<方案原文>
（不要自行更换架构、改模块划分或换数据流；方案里没写到的细节，留空并在结果里说明，不要猜）
```

- 开发者模式下**没有方案会被拒绝**（`--allow-no-plan` 可显式放行）；
- 有方案但系统想自己改架构时，这一档的裁判是人，所以只会 `needhuman` 问，不会悄悄替换；
- 甲方模式没有 plan，这一段是空字符串 → 提示词与原来完全一致（不引入新变量）。

## 五、怎么验证这档差别是真的（不是文档写着好看）

```powershell
cd prototype
python checks/check_policy.py     # 20 条断言，钉住三档互不相同
```

它断言的是：

- 甲方模式：裁判=远端、方案由系统定、本地判红**第一次**就升级、预算用尽后不再接管；
- 开发者模式：裁判=人、方案必须人给、硬判据红**也不自动接管**（要批准）、连续 2 次才提请远端；
- 只读模式：夜班被拒绝且**不写交付物**；
- 方案注入：开发者档写"只能照它做/不许猜"，甲方档写"细节自行决定"，空方案不产生任何提示词块。

## 六、这一节的边界（不许含糊）

- **GUI 还没有夜间任务面板**：现在甲方模式在界面里仍然是"单任务"（`/v1/tasks`），
  夜班只能走 `cli.py night` 或 `POST /v1/night`。这是已知缺口，不是"已经做完"。
- 远端接管写代码后**也要过全部机械判据**（契约 + 边界 + 签名 + SQL）：远端强 ≠ 必然对。
  它不过就返回窄证据、这张单算失败，绝不会因为"是远端做的"就放行。
- 开发者模式的"方案权威"目前只能约束**提示词与架构决策的归属**，不能机械验证
  "代码是否忠实于方案"——那需要方案本身可机判（例如列出模块与函数清单）。
- 甲方模式的上限确实是远端推理能力，但**判据仍然是机械的**：远端说对不算数，
  判据过才算。这一条永远不变，否则整份系统的可信度就没了。
