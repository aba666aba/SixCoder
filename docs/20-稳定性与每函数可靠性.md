# 20 · 稳定性：从"这次几分"到"哪个函数靠得住"

甲方问的是"能不能一步到位"。诚实回答不能靠一次运行，得靠**跨样本的每函数可靠性**。
这份文档定下方法、现状与下一步，避免再用单次成绩下结论。

## 二、三个问题分别怎么治

### 问题 1：`summarize` 这类"返回 dict"的函数（2/7）

它最容易错，也最适合机械化，因为契约已经把答案写死了：
`summarize([{"age": 10, "email": "a@x.com"}]) == {"count": 1, "avg_age": 10.0, "domains": {"x.com": 1}}`

**方案：字段级填充（dict 骨架 + 表达式槽位）**，比"让模型写整个函数"小一个量级：

1. 引擎先渲染骨架（键来自契约，不用模型猜）：

```python
def summarize(rows: list[dict]) -> dict:
    """<契约原文>"""
    result = {"count": None, "avg_age": None, "domains": None}
    # 每个键只填一个表达式
    result["count"] = __FILL_COUNT__
    result["avg_age"] = __FILL_AVG_AGE__
    result["domains"] = __FILL_DOMAINS__
    return result
```

2. 模型只输出**表达式映射**（不需要写函数、不需要转义三引号、不需要记住签名）：

```json
{"fields": {"count": "len(rows)", "avg_age": "round(sum(r['age'] for r in rows)/len(rows), 1)", "domains": "..."}}
```

3. 引擎把表达式填进槽位 → 语法闸门 → 判据（`keys` + 真 `call_eq`）验收。
   表达式写错，反馈只回"哪个键的表达式错了"，模型只需改那一行。

为什么这条路对：需要模型做的判断从"整个函数的控制流"缩小到"一个表达式"，
而示例/键名/签名都由引擎提供；出错时反馈也窄（一个键），符合"一次只做一件机器能验证的小事"。

### 问题 2：缺 import / 符号（6 条）

已做：`autofix` 补"用了模块却没 import"、"注解里缺的名字"、"测试文件没 import 实现符号"，
并区分"裸 import 不够"的情形（`from datetime import datetime`）；`add_import` 工作单不再要求符号。
**待办：一次干净重跑验证**（bench 已包含）。

### 问题 3：方差 / 只有 n=1

已做：`tools/bench_night.py`
- `analyze`：分析已有工作区，输出每函数可靠性 + 失败归因（秒级，不调模型）
- `run --runs N`：连跑 N 次（每次清空），自动汇总成同一张表

**规矩（写进流程）**：
1. 任何"能不能"的判断，样本 **n ≥ 3**，看每函数通过率而不是总分；
2. 改完机制必须跑同一条 `bench run` 对比前后，只认"某函数通过率上升"，不认单次涨分；
3. 样本跨引擎版本时只看趋势，不混算比例。

## 四、这一节的边界（不许含糊）

- 上表的 8/8 是**当时判据集**下的成绩。`docs/21` 加了边界矩阵之后，同一批产物重算是 7/8
  （`summarize` 在 `None` 年龄上会崩）。**跨版本比较只看趋势，不看绝对值**。
- bench 用的是**同一条需求夹具**（3 模块 8 函数）。换成真实项目，函数更多、契约更模糊，
  通过率只会更低，不会更高。
- 本地 7B 的上限已经在多轮实测里反复出现：它能写对单个函数，多模块一致性靠机制兜。
  机制能保证"错的东西不会被当成对"，不能保证"对的东西一定出现"。
