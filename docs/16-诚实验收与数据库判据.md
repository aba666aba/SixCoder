# 16 · 诚实验收：两种"假通过"和三条真判据

这份文档记录一次真实事故的全部证据链。它存在的理由只有一个：**"验收通过"这四个字必须是硬的**，
否则夜班报告越漂亮，早上交付的东西越不可信。

> 后续（`docs/21`）：这里最后那行"修完判据后 8/8"后来又被推翻了一次 ——
> 独立验收 19/19 全绿，`summarize` 仍然会在 `None` 年龄上崩。8/8 是旧判据集的产物，
> 同一批产物按现在的边界矩阵重算是 7/8。**"假通过"这件事有两层，这里是第一层。**
> 现在两种视角都补上了边界用例：`hq_verify` 从 19 条加到 25 条，同一批产物是 24/25、22/25，
> 判红的就是同一批函数。

## 一、事故时间线（全部为实测，非推演）

| 时点 | 引擎自报 | 独立验收（不共代码） | 差额说明 |
|---|---|---|---|
| 第一版夜班 | 8/8 函数"验收通过" | **13/15** | `store 端到端` TypeError、`summarize` NotImplementedError |
| 加稳压器后 | 8/8 | **16/17** | `store 端到端` 仍 TypeError |
| 修完判据后 | 8/8（有证据） | **19/19 PASS** | — |

13/15 与 16/17 里那一条失败的原文是：

```
FAIL store 端到端  TypeError: cannot convert dictionary update sequence element #0 to a sequence
```

出问题的代码只有一行：

```python
def fetch_all(conn):
    result = conn.execute("SELECT id,name,age,email,birth FROM people ORDER BY id ASC")
    return [dict(row) for row in result]      # ← 只有在设过 row_factory 时才对
```

`sqlite3` 游标默认吐**裸元组**，`dict(元组)` 必然 TypeError。而独立验收用的是
`sqlite3.connect(db)` 裸连接（没有 `row_factory`），所以它一跑就炸；
夜班自己那 8/8 却是绿的。

## 二、两层根因（为什么"8/8"是假的）

### 第一层：判据里没有这个维度

`conn: object` 这种参数，契约里拿不到样例（`SAMPLE` 表里没有 `object` 的可造值），
于是引擎判据在这一整个维度上是**空的**。`fetch_all` 的判据数 = 0。

### 第二层：空判据被当成通过

旧体检里有一句善意的兜底：

```python
if not sub:
    verified.add(f.name)      # 契约没给判据 → 存在即视为可用
```

这句话把一个数据库模块变成了"没检查 = 通过"。**没有证据就等于通过，是所有假通过的源头。**

## 三、现在有三条真判据（都可复现、都带反例）

### 1. 静态闸门 `gates.gate_db_rows`

证据类别 `static_rule`。只在**确定矛盾**时报红：文件里有数据库调用、全程没有
`row_factory`、却又对某个循环变量直接 `dict(x)`。报错直接给出唯一修法：

```
store.py:21 fetch_all() 对游标行直接 dict(row)：未设 row_factory 时行是裸元组，
必抛 TypeError → 改 dict(zip([d[0] for d in cur.description], row))，
或先 conn.row_factory = sqlite3.Row
```

不误杀已反例验证：`dict(zip(cols, row))` 放行、设了 `row_factory` 放行、无 SQL 的文件放行。

### 2. 引擎判据 `props.db_end2end`（真 sqlite 端到端）

从需求里的建表语句抽出列名与类型（`people(id INTEGER PRIMARY KEY, name TEXT, ...)`），
造两行数据，然后用**真实 sqlite 裸连接**跑一遍 `create_table → upsert → fetch_all`，
要求读回的 id 集合与写入一致。三个函数（建表/写/读）因此同时获得机械证据（`covers`）。

这条判据的意义在于：它不是"读代码觉得对"，而是"跑起来真的对"。

### 3. 体检不再给白信用

```python
if not sub:                 # 现在
    sub = typed_checks(...)  # 退一步用类型冒烟
if not sub:
    untested.append(f.name)  # 仍然没有判据 → 不计入"已验收"，写进交付报告的"无机械判据"列
```

并对同模块的静态闸门失败做**精确摘除**：只摘掉被点名那个函数，不连坐。

## 四、顺带修掉的两个真坑

### 坑 1：判据的类型错，比漏报更贵

`normalize_age(x: str)` 的契约是"范围 0..150，越界抛 ValueError"，而探针生成器
却给了**整数** `-1`。产物执行 `x.strip()` → `AttributeError`，判据据此连判 6 轮不过；
远端架构师每轮都被迫围绕"异常被自己 except 吞掉"编造根因，模型改了 6 次一个**本来正确**的函数。

修法：探针按参数声明类型写字面量（`str` 参数给 `"-1"` / `"151"`）。修完后 night3 从
"7/8 + 6 轮空转"变成 **8/8 一次通过**，且与独立验收 19/19 完全一致。

结论：**判据自己出错时，会把"质检"变成"瞎指挥"**。判据必须和产物一样被测试。

### 坑 2：add_test 让模型写测试 = 假通过

`add_test` 工作单过去走"符号替换"路径，模型写出来的 pytest 全绿而产物会 TypeError
（弱测试），定式化的 `调用 → 断言` 也没法从"生成代码无法解析"里救回来。

现在 `add_test` 不走模型：`iterate.add_engine_tests` 用**契约判据渲染 pytest**，
渲染前先跑一遍引擎判据（产物自己不过就拒绝写测试文件，避免往仓库里塞红测试），
渲染后跑 pytest，红了就删掉不留垃圾。

## 五、怎么复现这套结论

```powershell
cd SixAgent\prototype

# 1) 三个机制的自检（含反例：坏实现必红、三种正确写法必绿）
python checks\check_dbgate.py

# 2) 全部自检
python checks\run_all.py

# 3) 从零跑一次夜班（清空 workspace），再用独立验收脚本对账
python tools\night_fresh.py night3 --hours 0.5

```

`hq_verify.py` 与夜班本体**不共享任何代码**（自己连库、自己断言），它才是最终的裁判。

## 六、仍然成立的老结论

- 单次运行方差很大（同一套机制 4/8～8/8 都出现过），**不要用一次夜班证明能力**。
- 小模型（3B）在 3 模块基准上是 0/14：机制能救"最后一步走偏"，救不了"根本没读懂需求"。
- 目前最可靠的组合是：**结构化契约 + 引擎判据（含端到端）+ 静态闸门 + 远端架构师定位根因**。
