### 9.2 一整夜"覆盖停滞"的根因链（v39 → v45，7 次 replan，0 产出）

```
submit_topic(body, teacher_id) 的 teacher_id 被当成"路径里没有的主键"
  → ensure_web_router 判 bad → POST /api/v1/topics 不接线
  → 探针 404 → cap.api.validation 从 done 掉回 absent
  → cap.topic.create_draft / cap.batch.create 连续失败 3 次被自动 descope
  → 覆盖停滞 → replan → 再来一轮
```

**修复**：`_foreign_id_param(pn, path, method)` 区分主键 id 与外键/归属 id：

- 参数词干 == 路径资源（`batch_id` ↔ `/batches`）→ 主键，必须真有值（保住 11-07 的修复）
- 不相等且为创建型 POST/PUT（`teacher_id` ↔ `/topics`）→ 归属，给确定性默认值
- 带参数段时资源取**参数段前一段**（`/batches/{id}/run` → `batches`）
- 复数 `-ches` 去 `es`（`batches→batch`，只去 `s` 会得到 `batche` 误判）

实测（引擎重启后）：

```
[422] POST /api/v1/topics {"__invalid__":true}   ← 校验通过
[201] POST /api/v1/topics {"title":"t","quota":2} ← 返回完整草稿
[200] GET  /
[404] POST /api/v1/auth/login                     ← 下一个卡点
```

### 9.3 为什么"我能写而远端不能"（同为 DS-flash）

束缚不在模型能力，在**输入形态与交互方式**：

| 维度 | 会话内的我 | 系统里的远端（修复前） | 已修 |
|---|---|---|---|
| 代码形态 | 直接写 `.py` | JSON 字符串里的函数体，缩进靠 `\n    ` 手写 | ✅ 改 ```python 围栏 |
| 现有文件 | 可读任意文件全文 | 只有签名 + `NotImplementedError` 桩 | ✅ `read_plan` 全文 + `include_bodies` |
| 错误反馈 | 完整 traceback | `_tokens.cut(last, 1200)`，常切在关键行之前 | ✅ 4000 |
| 编辑粒度 | 最小编辑（定位→替换） | 整函数/整文件重写，遗漏即丢失 | ⚠️ 仍是最大差距 |
| 验证循环 | 改一行→跑→看错→再改 | 一次生成→判据→重来 | ⚠️ 结构性差距 |

**最根本的一条**：我做的是「最小编辑」，它被要求「重写」。
`decision: 跨函数/说不清位置，整文件重写一次` 是日志里反复出现的一行。
文件越大，整文件重写越容易丢东西、越容易语法错。

**若由我直接实现这一片**：
1. 读 `app/api/topics.py` 全文（现状已有 `submit_topic(authorization, body)`）
2. 只改这一处：把签名换成 `(body, teacher_id)`，函数体按契约重写约 12 行，其余 140 行不动
3. 跑一次 `TestClient` 冒烟 → 看 422/201 → 过了就收工

**会卡住我的环节**：只有第 3 步的"判据口径"（契约要求恰好 7 个键、字段名逐字一致）——
但我会用真实响应对照而不是猜，一轮就能对齐。

**能否用机制消除卡点**：能，方向是「补丁而非重写」——
让远端输出 `<<<<<<< SEARCH / ======= / >>>>>>> REPLACE` 块（aider 格式，模型很熟），
引擎做精确替换；替换失败就原样保留并报冲突。这能把"重写 150 行"降成"改 12 行"，

### 9.7 「编辑粒度 / 验证循环能否与会话内的助手一致」核验（2026-11-09）

**验证循环：能，而且 90% 已经实现好了，只是没接进写作路径。**

`core/remotetools.py::ToolLoop.run()` 是完整的多轮工具往返状态机：

```
messages = [system(GUIDE), user(instruction)]
for rnd in 1..max_rounds:
    reply = complete(messages)
    calls = parse_tool_calls(reply)
    if not calls: break
    for call: ok, out = _run_tool(...)      # 真实执行
    messages += [assistant(reply), user("工具结果：" + results)]   # 回灌
```

六个工具：`read_file / list_files / grep / run_tests / static_analysis / write_memory`，
带受保护区只读守卫。实测（注入假模型）2 轮往返正常，工具结果确实回灌。

**但 `ToolLoop(` 的调用点只有三处**：
`check_protected_zone.py`、`check_remotetools.py`（两个测试）和 `server.py:557`（一个 HTTP 端点）。
`core/author.py` 里只有一行：

```python
if tool_loop:
    prompt = prompt + "\n\n" + _rtl.tool_loop_guide()   # 只追加说明，不解析/不执行/不回灌
```

而 `tool_loop=True` **没有任何调用点**。即：机制建好了，从没进主流程。
这与 §9.1「`read_plan` 只接整文件模式、没接片段模式」是同一个病。

**编辑粒度：也能，但需要新写一小块。**
让远端输出 `<<<<<<< SEARCH / ======= / >>>>>>> REPLACE` 补丁块（aider 格式，
模型训练里见过），引擎做精确字符串替换：唯一匹配才应用，冲突就原样保留 + 反馈重试。
约 50 行，无现成实现，但失败可检测，比整文件重写安全得多。

**两者难度不同**：
- 编辑粒度 = 换输出协议 + 一个 apply_patch（局部，回退路径完整）
- 验证循环 = 把已实现的 `ToolLoop` 接进写作路径（组件现成，但要处理
  max_out / 用量记账 / 阶梯档位，不能简单替换 `remote.complete`）

**残留的本质差异**：会话内有"人在环"，可随时换方向；夜班无人值守只能按判据走。
这个用「缺口机制 + 检查点」缓解，不算硬伤。

**下一步（未做）**：先接"诊断回路"——写作失败后，用 `ToolLoop` 带真实
`run_tests` / `static_analysis` 输出生成证据，替换当前的压缩判据摘要。
不改生成逻辑，风险最低，且直接把「验证循环」用起来。

### 9.15　立铁律：本地是远端的**放大器**，不是缰绳（11:20–11:40）

#### 9.15.1 为什么这条要立成铁律（用当晚数据说话）

### 9.29 输出上限彻底断开（2026-11-09 19:30 用户指令）

追下去发现真相比"限制输出"更糟 —— 它**既没限制远端，又在害远端**：

|---|---|

3. **`core/remote.py: complete`** —— 回传 `finish_reason`（原来在内部用完就丢，调用方拿不到）。
4. **`core/remotetools.py: ToolLoop`** —— 支持 `max_out`（工具路径此前完全不传，

### 9.31 回收按「删除条目数」限速 + 清理失败不得打死引擎（2026-11-09 22:45）

夜班连续两次 `exit 1`，stderr 是宿主日志：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
{"count":79,"threshold":50,"scope":"turn",
 "targets":["F://...//.sixcoder//tmp//.gc-1794235521-45"],"targetCount":1}
```

#### 9.31.1 真正的坑：宿主统计的是**条目数**，不是顶层目录数

| 我以为 | 实际 |
|---|---|
| "限速 45 个目录 < 阈值 50" | 45 个探针目录**每个还含 1 个文件** → 实际删除 **79 条** > 50 → 被拒 |
| `except Exception` 能兜住 | 宿主抛的是 **BaseException 子类** → **漏网** → 异常冒泡**直接把夜班进程打死** |

第 2 条最隐蔽：`rmtree` 在 `try` 里、外层 `except Exception` 也写了，
但异常类型不在 `Exception` 分支里，所以清理失败 = 引擎崩 = 夜班 exit 1。

#### 9.31.2 修法

1. **按条目数分批**：新增 `_count_entries()`（用 `os.scandir` 粗估目录树的
   文件+子目录数，宁可高估），每批删除条目数 **≤ 40**（阈值 50 之下留余量）。
   批次划分从"每 N 个目录"改成"每 N **条**"。
2. **删除动作兜 `BaseException`**（`probe.gc_scratch` 与
   `company._night_inner` 的开跑钩子**两处**都要兜）：
   清理失败只是"没清干净"，批次留在盘上、下轮再收，
   **绝不能带走引擎**。
3. 目录树仍先用 `rename` 归集再一次性 rmtree（rename 不走宿主那层包装，
   避免每目录起一个 node 子进程）。

#### 9.31.3 实测

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 一次回收 200 个 | 被保护拒（count=79>50），进程死 | **成功，11.7 秒，exit 0** |
| 逐个删 36754 个 | 34 分钟才删 4000（每目录一次 node 子进程） | 已被 rename 归集法取代 |

自检：`check_tmp_hygiene` 补 [6] 段 6 条断言
（按条目数限速 / `_count_entries` 存在 / 两处 `except BaseException` /
30 目录 61 条能被拆批清完 / 不留 `.gc-` 残骸）—— 全部通过。

**清理类操作必须"失败不致命"**。引擎做的每一个破坏性动作（删目录、回滚文件）
都要假设它可能被宿主的安全网拒绝 —— 拒绝是**正常业务分支**，不是异常。

### 9.33 工具循环吞掉答案（原生 function calling 口径没跟上）（2026-11-09 23:25）

原生 function calling 下，模型请求工具时 `content` 通常是**空的** ——
所以最后一轮如果远端**还在调工具**，`last` 就是那个空字符串，
前几轮已经写好的正文被覆盖掉 → 上层解析不到任何 JSON → 整轮废弃。

日志证据：`tools=5 rounds=3` —— 5 个工具调用分布在 3 轮，
其中至少 1 轮是"纯工具轮"，答案就在被覆盖的那一轮之前。

**修**：只有"这一轮没有再调工具、且正文非空"时才更新答案
（`_last_with_text`），纯工具轮不碰它。

**② GUIDE 还是 XML 协议时代的**

`GUIDE` 里全是 `<tool name="read_file" path="..." />` 这种 XML 示例，
但请求走的是**原生 function calling**（`tools` JSON Schema）。
两件事同时错：
- 远端看到 XML 示例，却面对原生 tools schema → 困惑；
- **GUIDE 里完全没提"最终要输出什么格式"** → 远端调完工具就停。

**修**：GUIDE 改成原生口径（说明"直接按 schema 调函数，不要输出 XML"），
并新增一节「**最重要的一条：最终必须给出答案正文**」，
明确"调用工具只是中间步骤，查够后必须停止调工具、用普通消息给最终答案"。

**③ 补收尾追问**

跑满轮次仍没给正文 → 再追问一次，但**这一次不挂 tools**
（`allow_tools=False`），只问"不要再调用任何工具，现在直接给最终答案"。

#### 9.33.2 验证

行为级断言（`check_remote_tools` 补 [4] 段 7 条）：
- 源码层：答案只在"无 tool_calls 且正文非空"时更新 / 有收尾追问 /
  追问不挂工具 / GUIDE 是原生口径 / GUIDE 要求给最终答案；
- **行为级**：伪造"三轮都在调工具、正文全空" → 收尾轮拿到答案 ✅，
  且调用次数 = 4（3 轮工具 + 1 轮收尾）。

顺带把 `check_remote_tools` 里旧的 `name="read_file"` 断言改成查工具名本身
（断言的**意图**是"GUIDE 必须提到每个工具名"，不是"必须是 XML 形态"）。

#### 9.33.3 教训

**原生工具协议下，"最后一轮的内容"不等于"答案"**。
凡是"模型可以多轮交互"的循环，都必须区分：
- **中间轮**（在请求工具 / 在执行动作）
- **收尾轮**（给出最终产物）

只取 `messages[-1]` 的内容，在多轮工具场景下必然拿到空。

### 9.34 网络不通要把每个模块各判一次失败 → 改成原地等恢复（2026-11-10 00:50）

夜班 verified 从 4/35 涨到 **29/35**（远端真在写码了），
但日志里出现新的失败形态：

```
author_tools   path=matching_core/greedy.py tools=0 rounds=1
order_failed   reason=远端调用失败：[网络不可达] 请求失败：URLError: <urlopen error [Errno 11001] getaddrinfo failed>
decision       path=matching_core/greedy.py reason=偶发失败（限流/超时），同档重试
isolate_rollback ...
author_start   path=matching_core/manual.py ...     ← 换下一个模块
```

#### 9.34.1 两个真 bug

**① 整文件路径漏了 `network_unreachable`**

`author_bodies`（函数体路径）早就返回 `network_unreachable`，
`author_module`（整文件路径）的 `_remote_failed` 分支**漏了**这个字段。
于是 company 层拿到一个"远端调用失败"，**分不清是断网还是远端答错**。

**② 断网被当成"这个模块失败"，然后换下一个**

原口径：网络一抖 → 该模块判 order_failed → 换下一个模块 → 下一个也断 →
整轮下来 0 产出，还被记成"模型不行"。

**正确口径：网络不通时原地等网络恢复，然后重试同一个模块。**
（用户早就反馈过这一点：断网恢复后远端没用恢复。§9.30 只修了单次调用内的重试窗口，
没修**跨模块**这一层。）

#### 9.34.2 修法

1. `author.py` 整文件路径补 `network_unreachable`（reason 也改成"远端网络不可达
   （等网络恢复后可重试）"，和函数体路径口径一致）。
2. `company.py` 新增 `_wait_network(ws, emit, max_seconds)`：
   **真的发一次极小的远端请求探活**（比探 DNS 准 —— DNS 能解析不代表 API 能连上），
   每 15 秒探一次，最长 `_NET_WAIT_SECONDS`（默认 900 秒，可用环境变量调）。
3. `_write_one` 里遇到 `network_unreachable`：
   **等网络恢复 → 重试同一个模块**（`_write_one(rel, _net_try + 1)`），
   最多原地重试 3 次（防网络反复抖动导致无限递归）；
   等不到就记 `stats["network_down"]`，**不记成模块能力失败**。

#### 9.34.3 断言

`check_network_recovery` 补 [6] 段 9 条：
author 两条路径都有 `network_unreachable` / company 有 `_wait_network` /
重试同一模块 / 有上限 / 不记成模块失败 / 等待时长可配 / 行为级调用验证。

### 9.36 假绿洞二：**判据引擎自己没跑起来**的函数被 e2e 洗成"已验收"（2026-11-10 15:20–15:50）

#### 9.36.1 缺陷

`iterate.inspect` 里，`hard_failed`（判红）、`untested`（没判据）是两个分开的账本，
但**"判红"和"判不了"都归进了 `untested`** —— 判据引擎自己跑不动（探针起不来、
输出不可解析）与"契约太薄造不出判据"被混为一谈。

于是 e2e 业务流一跑通，就会把这些函数**加进 `verified_names`** →
`verified >= funcs` → **模块判绿、标 done、再也不碰**，
而这个函数**从头到尾没有任何机械判据验证过**。

关键点：系统**在别处已经区分了"引擎坏了"和"产物错了"**——
`company.needs_work_state` 遇 `engine_errors` 直接不派单，
`company.no_work_reason` 如实报"引擎判据自身跑不动（不是产物错）"。
**唯独 e2e 合并这段没区分** —— 这正是 11-09 铁律"机制问题被记成能力问题"的同一个坑，
只是方向相反：那次是机制问题被记成**产物不合格**，这次是机制问题被记成**产物合格**。

#### 9.36.2 修法

新增逐函数账本 `engine_failed`（`core/iterate.py`）：

| 场景 | 记账 | e2e 合并时的处理 |
|---|---|---|
| 判红（`hard_failed`） | 已有 | 不给 e2e 信用（`check_bounds` [5] 早就钉住） |
| **判据引擎起不来** | **新增 `engine_failed`** | **不给 e2e 信用**（本次修的洞） |
| 契约太薄造不出判据 | 仍在 `untested` | 给 e2e 信用（e2e 是它唯一的证据，设计如此） |

**精准归因，不搞模块级一刀切**：`engine_failed` 记到**函数**，
所以一个模块里别的函数照常拿 e2e 信用，不会连坐。
模块级判据（`db_end2end`/`seq`）跑不起来时，归因到它 `covers` 的那些函数。

也不会造成"判红却没人修"的新死锁：`engine_errors` 的模块本来就不派单
（`needs_work_state` 直接返回 False），所以判红只是**如实报出**，
不会凭空多出一堆待派单的工作量。

### 9.41　18:00 夜班两个真 bug：探针永久挂死 + 停机线拿全量账本当本项目（18:00–18:25）

#### 9.41.1 探针挂死（把整支夜班卡死 13 分钟）

症状：18:00 起跑的夜班 18:01 开始端到端观测，18:05 到超时后**零输出零花费挂了 13 分钟**。
py-spy 栈：`_http_exec → subprocess.run → Popen._communicate → Thread.join`。

根因：`subprocess.run(capture_output=True, timeout=...)` 到期只 kill **直接子进程**；
子进程若再起孙进程（uvicorn / worker / 后台线程）并继承了 stdout 管道，
`communicate()` 仍要等**所有写端关闭** → 孙进程活着就永远等下去。四处同样写法
（`_run_cli` / `_run_call` / `_run_pytest` / `_http_exec`）全部中招。

修法：新增 `core/probe.py:_run_child` —— 输出写**文件**（不用管道）+ 超时 `taskkill /F /T`
杀**整棵进程树** + 只读已写下的内容判定（判定口径不变）。
自检 `checks/check_probe_timeout.py`（11 断言）：超时+孙进程持有 stdout 必须 20 秒内返回；
子进程早退但孙进程活着不许阻塞；AST 级钉子禁止任何子进程调用再用 `capture_output`/`PIPE`。

#### 9.41.2 停机线口径错配（"中午能跑，晚上一启动就收工"）

### 11.4m　**行级补丁的锚点不支持多行 → 补丁全被拒 → 退回整文件重写**（2026-11-11 19:00–20:20 实测）

**症状**：本轮夜班（19:02 启动，PID 14356）在 `app/services/llm.py` 上反复出同一个错：
```
patch_rejected  path=app/services/llm.py reason=补丁未应用：第 40 行原文对不上：
  期望 "'direction': direction_text,\n           "，实际 "'direction': direction_text,"
```
注意期望值里有个 `\n` —— **远端给的锚点是多行的**，而引擎只按**单行**比对。
同一批文件里还有两例同型（`app/models.py` 第 1187 行、`app/api/topics.py` 历史上亦有多行锚点）。

**根因（已机械复现，非推测）**：`core/patch.py:apply_patches` 的替换分支是
```python
cur = lines[n - 1]
if cur.strip() != old.strip():      # ← 拿一整行去和多行 old 比
    rejected.append(...)
```
`old` 若是多行片段，`old.strip()` 仍含换行 → **永远不等于**任何单行 → 100% 被拒。
实测（`D:/Python/python.exe` 直接调真函数）：
```
多行锚点 ok=False  rejected=['第 3 行原文对不上：期望 \'return {\\n        "k": 2\'，实际 \'return {\'']
单行锚点 ok=True   rejected=[]
```
**这是"宁可不改，也不许乱改"的安全规则被误伤**：守卫本身是对的（防止改错行把对的代码改坏），
但它**没有区分"单行锚点"和"多行锚点"**，把合法的多行替换也判成"原文对不上"。

**为什么这条会造成"覆盖倒退"（本轮实测）**：
补丁被拒 → 引擎拿不到可用的行级修复 → 退回**整文件重写** →
整文件重写会连带改掉该文件里**已通过的能力**（`app/models.py` 承载 9 条 done 能力，
`app/services/topics.py` 承载 `cap.topic.offline`）→
`regress_guard` 把它列为"退化的模块要强制重写"→ 下一轮又整文件重写 → **循环**。

本轮 `coverage.jsonl` 的状态变化印证了这个机制（19:04:56 与 20:11:34 两次观测）：
```
19:04:56  cap.topic.create_draft  absent → done
          cap.topic.offline       done → absent      ← 整文件重写打掉了已通过的
          cap.auth.forbidden_role done → absent
20:11:34  cap.topic.create_draft  done → absent      ← 又被打掉一次
          cap.topic.offline       absent → done
          cap.llm.generate_candidate absent → done    ← 本轮唯一净增
```
**净增 +1，但伴随 2 次倒退** —— 指标 §20.8「每片净增 ≥2 且倒退 = 0」**未达标**。
注意这里的"倒退"与 §9.50.8 那类"落点算错"不同：**判据没错、探针没错，
是引擎自己在同一批文件上反复整文件重写，把上一轮自己刚做对的东西打掉。**

**结论（下一步该动哪）**：
1. **补丁锚点支持多行**：`apply_patches` 的替换分支应支持 `old` 含换行的情况
   （按整块文本比对 + 块级替换，而不是逐行 `strip()` 比对）。
   这条**零 token、纯本地**，收益是把"补丁被拒"从"退回整文件重写"这条危险路径上摘下来。
2. **整文件重写的前置复验**：`_caps_done_by_file` 已经能算出"这个文件承载几条已 done 能力"
   （实测 `app/models.py` → 9 条），但**整文件重写这条路没有强制走复验**，
   而"只回函数体"这条路有。**两条粒度路径的复验强度不对等** —— 这是同一个坑的第二个入口。
3. 本轮还暴露一个**信号噪声**：架构师给出的 `root_cause` 是自相矛盾的话
   （"返回的 status 是 `'created'` 而不是路由探针要求的 `'created'`"），
   说明契约自洽化（§9.50.2）仍有漏网 —— 诊断文本自相矛盾时，说明判据侧还没真对齐。

**教训一句话**：**"宁可不改"的安全规则，必须区分"不敢改"和"不该这样改"。**
守卫拦住了越界改动，但没拦住合法改动 → 合法改动被拒 → 引擎走更危险的兜底路径 → 净倒退。
**每次加保守规则时，都要问一句："它会不会把合法的请求也挡在门外？"**

  拿它当补位 → 分配算两遍 → "重复分配""超容量"假红（实测踩过）。宁可少一条断言，也不断言错。
- 自适应路径下 **rank / summary 常常不存在**（排序与汇总是内嵌在 DA 里的）→ 对应断言**跳过**。
  所以自适应路径的断言数是 **6 条**（老路径 8 条以上）。
- **业务流跑起来后，交付报告的"业务流"一栏会从"不适用"变成"通过 N 条不变量"** ——
  这是交付质量的实质提升（从"零件级证据"到"跨模块不变量也过了"）。

**教训一句话**：**"判据不适用"和"判据没用"是两件事。**
引擎诚实标了"不算通过"，没有假绿 —— 但**"认不出"不等于"不存在"**：
一个项目有没有业务链，取决于**判据能不能认出它的形态**，不取决于项目本身。
**判据的识别层（按名字匹配）比判据本身（那 9 条不变量）更脆。**
