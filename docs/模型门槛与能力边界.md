# 模型门槛与实测能力边界

> 本文只写**实测出来的**数字，不写宣传口径。数据来源：同一份多模块需求、
> 同一套闸门与判据（我手写、模型不可见），只换模型。
> 复现：`python cli.py run --repo <dir> --requirement-file hq_requirement.txt --model <模型>`

## 一、测试用的基准工程

`hq_requirement.txt`：CSV 数据清洗与入库，3 个模块 / 8 个函数 / 含 SQLite 与统计。

| 模块 | 函数 |
|---|---|
| `clean.py` | normalize_age / parse_date / clean_email / clean_row |
| `store.py` | create_table / upsert / fetch_all |
| `report.py` | summarize |

验收方式：`hq_verify.py` 内置 **14 条独立判据**（示例、越界抛错、SQLite 端到端、统计口径），
不依赖模型自写的测试。

## 二、实测结果

| 模型 | 运行环境 | 速度 | 独立验收 | 用时 | 测试数 |
|---|---|---|---|---|---|
| `qwen2.5-coder:3b` | GPU（4GB 显存全量） | 16.5 tok/s | **0/14** | ~4 min | 18 |
| `qwen2.5:7b` | **CPU**（i7-13700H） | 6.9 tok/s | **10/14 → 11/14** | 9–10 min | 18 → 35 |

### 2.1 加上全套机制之后再看 3B（`projects/night3b/`，最新实测）

上面那次是"裸跑"。后来引擎补了契约判据、静态闸门、SQL 端到端判据、策略阶梯，
再让 3B 当工人跑同一条夜班（10 轮、关闭远端、5.3 分钟）：

| 指标 | 3B（全套机制） | 7B（全套机制，同一条需求） |
|---|---|---|
| 引擎机械验收 | **2/8** | 8/8 |
| 独立验收（不共享代码） | **2/16** | 19/19 |
| 主要失败形态 | **`生成代码无法解析 (ParserSyntaxError)` 占绝大多数**，其次 NameError / 校验缺失 | 局部边界错误，能按证据改 |

结论很硬：**机制救不了 3B。** 它的瓶颈不在"推理不够聪明"，而在**连结构化输出这一关都过不去**——
JSON 里的 `code` 字段经常渲染不成合法 Python，等于工人连"交作业"都做不到。
3B 的速度优势（16.5 vs 6.9 tok/s）完全被"交不出可验收的东西"抵消：按**每交付一个验收通过的函数**算，
3B 比 CPU 上的 7B 差一个数量级。

所以：**3B 不能当默认工人**。它唯一还有位置的场景是"极窄单函数改写 + 引擎判据兜底"，
而且即便如此，7B 在 CPU 上的端到端产出仍然更划算。

结论：
- **3B 不能完成多函数模块**：它能把桩换成实现，但会跳过部分函数、丢参数、写错跨文件导入，
  14 条判据一条都不过。
- **7B（哪怕纯 CPU）能完成大部分**：11/14 通过，剩下 3 条是"函数缺失 / 未实现 / 类型混用"
  这类局部错误，不是全盘失败。
- 7B 的代价是 **2.4 倍时间**；在 4GB 显存的机器上只能用 CPU 跑。

## 三、最低要求与推荐配置

> **硬门槛：本地模型 ≥7B。** 这条已经做成代码（`prototype/core/model_policy.py`），
> 不是建议：低于门槛的模型在四个入口都会被拒绝或自动替换（后端 `POST /v1/tasks` 返回 400、
> CLI 退出码 4、夜班/iterate 自动换合格模型或直接报错、界面下拉里标"不可选"）。
> 自检：`python checks/check_model_policy.py`。

| 用途 | 最低模型 | 建议 | 说明 |
|---|---|---|---|
| **单函数 / 单文件任务**（有测试或可判定示例） | **7B** | 7B | 3B 只在"单函数 + 极简签名"上偶尔通过；全套机制下仍是 2/8（实测） |
| **多函数模块（3+ 函数、含校验/边界）** | **7B** | 14B | 3B 实测 0/14；7B 实测 11/14 |
| **多模块工程（3+ 文件、跨文件依赖）** | **远端主力 + 本地手脚** | 14B–32B 或直接远端 | 7B 能写出大部分，但跨文件一致性与边界校验仍会漏 |
| **"通用编程助手"（对标 Cursor/Claude Code）** | **不建议用本地小模型** | 云端 API 或 32B+ | 本系统实测：3 文件级工程 0/6–3/6 节点、独立验收 0/3；差距是模型能力，不是闸门 |

**写进配置的最低门槛（本系统硬性要求）**

1. 支持 **JSON 结构化输出并且能产出可解析的代码块**（3B 实测在这一步就大量失败）；
2. 单次上下文能稳定容纳 **约 4k tokens**（我们的包体是 1.2k–2.2k，留一倍余量）；
3. 参数量 **≥7B**（`model_policy.MIN_PARAMS_B`，2024 实测下限；1.5B/3B 已被代码拒绝）；
4. 显存 ≥4GB 可全量跑 3B；7B 在 4GB 卡上会退化为 CPU（实测 6.9 tok/s，可接受但慢）。

## 四、远端模型的定位

### 4.0 关闭 thinking 到底省不省、会不会更费（实测）

甲方问得很关键：关思考省 completion，但会不会因为方案变差而反复更多次，实际更贵更慢？
用真实接力包做了 A/B（`prototype/tools/exp_thinking.py`，同一份包体、同一任务，
各跑 3 次；任务形态就是"远端救一个缺函数的实现文件"，因为失败证据已经在包里）：

| 配置 | 是否一次过本地闸门 | completion tokens（3 次） | 中位耗时 | 回答长度 |
|---|---|---|---|---|
| `thinking=off` | **3/3 通过** | 83 / 83 / 83（中位 **83**） | **1278 ms** | 233 字符 |
| `thinking=on` | **3/3 通过** | 571 / 504 / 393（中位 **504**） | 2930 ms | 约 226 字符 |

结论（限定在这个任务形态上）：
- 关思考 **completion 少 6.1 倍、快 2.3 倍**，通过率**没有下降**，写出来的代码长度几乎一样；
- 原因是**包体已经把"思考"做完了**：契约、失败闸门原文、目标文件全文、输出格式都在提示里，
  模型只需要照着填符号编辑 —— 这是提示工程替代推理的典型场景；
- **但样本只有 3 次、任务只有一种**。真正考验思考的是"开放式诊断"（架构师找根因、算法选择、
  跨文件一致性），那里关思考是有风险的：根因判断错 → 工作单派错 → 多烧好几轮。

因此推荐（**已实现**，见 `core/company.py` 的 `architect_turns / stall_rounds / think_on_used`）：
1. **符号级编辑 / 远端救火**：`thinking=off`（本实验支持）；
2. **架构师诊断**：先 `off`；若"已经问过架构师且仍无增长"才升 `on` 重问，**整夜最多升 1 次**
   —— 把"思考"当成升级阶梯里的一档，而不是开局就付费。时间线里会发 `architect_thinking` 事件，
   记录这一轮用的是 off 还是 on。

### 4.1 远端在本系统里做什么

远端（DeepSeek `deepseek-flash`）在本系统里是**主力**（本地当手脚、省 token）：

- 单次调用实测 `prompt 1.2k–2.2k / completion 240–590`，成本约 **$0.0005**；
- 同一包体二次调用前缀缓存命中 **90%**；
- 一次成功案例：本地 3B 卡住的罗马数字题，远端 1 次调用解决，成本 ≈ $0.0005；
- 相比"纯远端重写文件"的方案，本系统实测可省 **95%–99%** token 成本。

## 五、能力天花板（诚实记录）

| 场景 | 实测 |
|---|---|
| 单函数 + 可判定示例 | 稳定通过（3B 即可） |
| 4 模块记账工具（ledger） | 最好 4/8 节点，实现节点常 0/4 |
| 3 模块数据工程（本文基准） | 3B：0/14；7B：11/14 |
| 需要真正推理的算法题（罗马数字、区间合并） | 3B 会写出假绿；闸门能拦，但自己改不对；远端 1 次可解 |
