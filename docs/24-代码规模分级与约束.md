# 24 · 代码规模分级与约束体系（S / M / L / XL）

> 一句话：**约束的固定成本必须被它在该规模下拦住的问题覆盖。**
> S 级用架构测试是过度工程化；M 级没有架构测试是放任漂移；L 级没有可观测性替代逐行审查会形成吞吐瓶颈；XL 级没有人类架构 owner 则超出当前可验证的边界。

## 0. 为什么甲方模式必须"先声明规模"

同一套门禁在不同规模上的收益完全相反：

| 如果你不说明规模 | 系统只能这么办 | 后果 |
|---|---|---|
| 1 万行的小项目 | 按实测推断 → S 级 | 若你其实要长到 50 万行，早期没建架构约束，后期补的成本是重写 |
| 50 万行的系统 | 若误判成 S 级 | 架构测试、覆盖率地板全都不上 —— **等于没有约束** |
| 100 万行以上 | 若当成普通项目 | 无法给出"完全自主"的承诺，必须有人保留架构 owner |

所以系统现在的做法是：
1. **需求里写明**（`代码规模：M` 或 `@scale M`）→ 直接采用，不警告；
2. 没写 → 按仓库实测行数推断，**在交付报告里写明依据并警告**；
3. CLI 用 `--scale`、API 用 `scale` 字段、界面用「规模」下拉 —— 三处都通。

## 1. 分级总表

| 维度 | **S（<10 万行）** | **M（10–50 万）** | **L（50–100 万）** | **XL（>100 万）** |
|---|---|---|---|---|
| 常驻规则 | 一份 50–100 行 | 根 100–150 行 + 子目录 + 领域指南 ≤300 行 | ~100 行目录 + 按需加载 + Doc-gardening | 同 L，但治理文件**不可变** |
| 架构守护 | 人审口头维护 | 依赖方向测试（<15s） | 结构测试 + 自定义 Lint（报错内嵌修复指令） | 持续健康度指标 + 漂移检测 |
| CI 门禁 | 构建/类型/Lint/单测/secrets | +架构测试 +覆盖率 80% +PR 500 行软上限 | +变更行变异(≥70%) +安全扫描 +受保护区 +依赖白名单 | 持续验证回路（合并前 → 修改后即时） |
| 评审 | 逐 PR 人审 | 机器拦架构 + 人审 | 人类设边界 + 看聚合指标 | 同 L + 不可变核心契约 |
| 上下文 | 根文件足够 | 工作集声明 + 反向依赖检查 | 可观测性作为 Agent 感知器官 | 只守少数系统级不变量 |
| 熵管理 | 人工定期清理 | 轻量扫描，人工合并 | 后台 Agent 自动扫描 + 自动合并 | 持续指标反馈 + 人类干预极端 case |
| 实证锚点 | 15,000 行无强制即接近崩溃 | 150,000 行实施后无可测量漂移（调试约 -15%） | 100 万行 / 1,500 PR / 0 行人工编写（内部 Beta） | **无公开的从零生成直接上线案例** |

## 2. 每一级"明确不做"的事（这才是分级的关键）

| 级 | 不做 | 理由 |
|---|---|---|
| S | 架构测试 | 配置成本通常高于它拦住的问题；边界由 PR 人审口头维护 |
| S | 覆盖率地板 | 小程序硬压覆盖率会诱导写垃圾测试 |
| S | 变异测试 | 成本高于揭示的问题 |
| S | 依赖白名单 | 只有维护成本；改为 PR 说明理由 + 人工确认 |
| S | 受保护区自动拒绝 / 健康度指标 / 自动合并清理 / 工作集声明 / 子目录 AGENTS.md | 这些机制在 10 万行以下的分流收益尚未出现 |
| M | 变更行变异测试 | 50 万行以下成本高于收益（覆盖率仍有效） |
| M | 依赖白名单 / 受保护区 / 健康度指标 / 自动合并 | 从 L 级起才有足够吞吐与风险面 |
| L | 持续架构健康度指标 | 仍以 PR 级门禁为主，指标体系留到 XL |
| XL | — | 已无更高一级可省；诚实做法是缩小目标或增加人类介入 |

## 3. 升级触发条件（满足任一即升级）

- **S → M**：> 8–10 万行；模块 > 5–8 个；出现第二个长期贡献者；事故开始与跨模块边界穿透相关。
- **M → L**：> 50 万行；模块 > 15–20 个；生成速度开始超过人工审查吞吐；出现跨团队公共 API 契约。
- **L → XL**：> 100 万行；需要从零生成长期自主演进的新系统；**架构骨架本身要由 Agent 提出**（最根本的范式切换点）。

## 4. 系统里这些约束落在哪

| 组件 | 作用 |
|---|---|
| `core/scale.py` | 级别定义、实测计数、定级解析、门禁计划（跑什么/不跑什么 + 理由）、报告渲染、**升级触发检测** |
| `core/arch.py` | 按档门禁：架构依赖方向、覆盖率地板、变更行变异、依赖白名单、健康度与**漂移**、diff 规模 |
| `core/quality.py` | 第二批门禁：类型检查、lint（带修复指令）、熵管理扫描 |
| `core/governance.py` | 治理文件生成（AGENTS.md/子目录/领域指南/架构约束）、工作集声明、反向依赖、**指纹锁定** |
| `core/debt.py` | 临时方案台账（只追加、到期按档处理） |
| `company.night` | 开跑先定级 → 生成治理文件 → 发 `scale` 事件 → 按档跑门禁 → 交付报告写「规模与约束等级」 |
| `cli.py night --scale/--max-cny/--remote-model` | 命令行显式声明；不写则警告并推断 |
| `/v1/night` + 界面「规模」下拉 | 甲方模式把"目标规模"变成必填项 |

### 4.1 规则 → 落点代码（逐条对应，便于审计）

| 分级规则 | 落在哪 | 自检 |
|---|---|---|
| 常驻规则文件（S 一份 / M+ 子目录与领域指南） | `governance.render_agents_md` / `write_governance` / `write_guides` | `check_flow.py`、`check_tier4.py` |
| 硬性禁令 + **don't-do 配对** | `governance._hard_rules` / `_dont_do_pairs` | `check_flow.py` |
| 治理文件不可变（XL） | `governance.lock_governance` / `verify_governance`（sha256 指纹） | `check_tier4.py` |
| 核心契约不可变（签名/schema） | `governance.sig_digest`（函数签名 + 表列指纹） | `check_tier4.py` |
| 架构依赖方向测试（M+） | `arch.gate_layers`（ast 自算，零依赖） | `check_flow.py` |
| 覆盖率地板 80%（M+） | `arch.gate_coverage`（真跑 coverage；没装如实说测不了） | `check_tier4.py`、`check_flow.py` |
| 变更行变异 ≥70%（L+） | `arch.gate_mutation_changed`（无 git diff 时退化全文件并明说） | `check_flow.py` |
| 依赖白名单（L+） | `arch.gate_dep_whitelist` + `write_dep_whitelist` | `check_flow.py` |
| 受保护区自动拒绝（L+） | `scale.protected_hits` + `_author_round` 拒绝 | `check_scale.py` |
| 持续健康度 + 漂移（XL） | `arch.health_metrics` / `health_drift` / `gate_health` | `check_tier4.py` |
| 即时反馈（XL） | `_author_round` 每次写成功后发 `instant_health` | `check_batch2.py` |
| 类型检查 / Lint / 熵管理 | `quality.gate_typecheck` / `gate_lint` / `gate_entropy` | `check_batch2.py` |
| 报错内嵌修复指令（L） | `core/lint.py` 的 `FIXES` 表（每条规则都给了改法） | `check_batch2.py` |
| 工作集声明 + 反向依赖（M+） | `governance.workingset` / `gate_workingset` / `reverse_deps` | `check_flow.py` |
| 单 PR 单主题（等价物，M+） | `_author_round`：M+ 一轮只改一个模块 | `check_batch2.py` |
| 改动规模软上限（M+ 阻断，可带理由豁免） | `arch.gate_diff_size` + `SIXAGENT_DIFF_CAP_REASON` | `check_tier4.py` |
| 熵管理 = 临时方案台账（M+ 报告 / L+ 阻断） | `core/debt.py` | `check_debt.py` |
| 聚合指标（L 级"看见一切"的最低实现） | `tools/metrics.py` | `check_batch2.py` |
| 升级触发 | `scale.upgrade_hint` → `scale_upgrade` 事件 | `check_tier4.py` |
| 质量阈值按档（12/10/8） | `scale.quality_limits` → `gates.gate_quality_metrics(level=)` | `check_tier4.py` |
| 每档重写次数（S3/M2/L1） | `scale.write_per_tier` | `check_scale.py` |
| 默认时间预算（0.5/2/6/12h） | `scale.default_hours` → CLI / `/v1/night` | `check_scale.py` |
| 甲方模式两段式 Plan 门禁 | `SIXAGENT_CLIENT_PLAN_GATE=1` → 写 `plan.md` 后停下等人批 | `check_batch2.py` |

> 这张表的用途：**每条规则都必须能指到代码、指到自检**。
> 指不到的（目前只有"性能预算""CI/CD""对抗性评审"三条）就写在 docs/17 §三 里，不许假装有。

## 5. 诚实边界（不许含糊）

- 上面各级的"实证锚点"都来自公开实践，但它们都建立在**人类设计了架构骨架**之上；
- **XL 级"只提需求 → 100 万行以上生产级系统完全自主"没有任何可验证证据**，系统不会承诺这一点；
- 因此 XL 级在本系统里的定位是：**受控的大规模实现与演进**，人类保留架构 owner。
