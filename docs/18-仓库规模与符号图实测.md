# 18 · 仓库规模与符号图实测（决定"能不能上万级仓库"）

> 这份文档是从已删除的研究分支 `graft_demo/` 里**留下的唯一有价值的东西**：实测数字与结论。
> 代码没进产品（0 处引用），留着只会让仓库看起来比实际复杂，所以删了；方法足够简单，需要时可按本文重做。

## 一、为什么要测这个

产品的定位是"给一条需求，在本机把代码写出来"。一旦目标仓库不是从零开始，而是**万级文件的存量仓库**，
第一个问题不是模型聪不聪明，而是：**能不能在几百 token 的上下文里只喂"那一个符号"**。
如果做不到，4GB 显存的小模型根本没资格参与。

## 二、环境与语料

| 项 | 值 |
|---|---|
| 机器 | i7-13700H（20 线程）/ 31.7 GB / Python 3.12.10 |
| 语料（10k 点） | modelscope + transformers + torch + sympy + pandas + networkx = **10,224 文件 / 4.00M 行 / 266 MB** |
| 语料（20k 点） | 整个 `site-packages` = **19,319 文件 / 7.45M 行** |

## 三、总表（全部为实测）

| 指标 | 3 文件 demo | 10,224 文件 | 19,319 文件 |
|---|---|---|---|
| 符号数 | 5 | 186,010（函数 159,308 / 类 26,702） | 347,670 |
| 调用边 / 导入边 | 5 / 2 | 1,220,084 / 147,599 | 1,924,517 / 251,666 |
| 全量建索引 | — | **71.5 s**（8 进程） | **132.1 s** |
| 增量重建（改 5 文件） | — | **1.34 s** | **2.26 s** |
| 索引库大小 | — | 575 MB | 874 MB |
| 进程 RSS | 30 MB | **70 MB** | **78 MB** |
| 符号定位 / 调用者查询 | — | 0.02 ms / 0.07 ms | 0.02 ms / 0.08 ms |
| 上下文切片 | — | 0.05 ms → **352 tokens** | 0.08 ms → **707 tokens** |
| 单次编辑闭环（解析→改图→渲染→语法闸门） | <1 ms | **20 ms** 中位 | **58 ms** 中位 |
| 保真渲染（逐字节 == 原文） | 3/3 | **1000/1000 = 100%** | — |

## 四、六条可复用的结论

1. **规模是线性的，不是爆炸的**：文件 ×1.89、行数 ×1.86、耗时 ×1.85。两个实测点足以判定线性。
2. **"整仓常驻 CST"这条路直接出局**：单文件常驻 CST 约 488 KB，1 万文件 ≈ 4.7 GB；
   索引 + 按需解析的 RSS 只有 **70 MB**。所以索引化不是优化，是唯一可行解。
3. **上下文与仓库规模无关**：整文件喂法中位 3,597 tokens，符号切片 **352 tokens（1/10）**；
   2 万文件下是 707 tokens。小模型只要有几百 token 的有效窗口就能参与万级仓库。
4. **保真渲染这个根基假设成立**：随机抽检 1,000 个真实文件，`libcst.parse → .code` 与原文
   **逐字节相同，0 差异、0 解析失败**。（产品里 `core/symedit.py` 就建立在这条上。）
5. **瓶颈是模型，不是 harness**：编辑闭环在 2 万文件下也只有 58 ms，而单个节点的墙钟是 10–35 s，
   全部是模型时间。所以"先优化引擎"通常是在优化 0.3%。
6. **诚实的问题：调用边 60.9% 指向重名符号**
   （186,010 个定义里只有 80,796 = 43.4% 名字唯一；最易混淆 `__init__×15,961`、`forward×11,251`）。
   含义：万级仓库里做"变更影响分析"，对 45.6% 的边只能给**候选集合**而不是精确目标。

## 五、对产品的影响（写进缺口清单）

结论 6 正是 `docs/17` §三 里"变更影响分析"没做出来的技术根因：不是没时间做，而是
**在重名普遍存在的真实仓库里，影响面只能给"候选集 + 置信度"，不能给确定答案**。
要做就得先补类型/接收者推断，那是另一个量级的工程。

结论 3、4、5 反过来支持了当前架构的取舍：
- 每次只改一个符号（`symedit` 保真渲染）——成本与仓库规模无关；
- 上下文只喂目标符号 —— 小模型也能用；
- 不要在引擎性能上纠结 —— 模型才是耗时来源。
