# 19 · 三种模式：甲方模式 / 开发者模式 / 只读模式

同一个系统，三种授权档位。名字固定，不叫"完全授权"那一套。

| 模式 | 人工审核 | 一句话 |
|---|---|---|
| **甲方模式** | 全部放行（无人值守） | 甲方只提需求，不看实现，夜里跑完早上看交付报告 |
| **开发者模式** | **关键节点必须人批**（不会自动放行） | 给开发者做细节化版本控制与代码写作 |
| **只读模式** | 无写操作，无处可批 | 只读代码，用于成品意图了解与改进分析 |

代码位置：`core/permissions.py`（档位与能力矩阵）、`core/approval.py`（人工审核门）、
`core/guards.py`（五个关键节点守卫）、`core/sandbox.py`（工作区牢笼）。

---

## 一、甲方模式

**给谁用**：甲方。提一句话需求，不需要知道具体实现。

**行为**
- 人工处置**全部放行**（`auto_approve=True`）：夜里无人值守也能一路跑完，不会卡在等人
- **从 0 到 1**：空仓库也能直接建成可交付成品（骨架 → 工作单 → 实现 → 机械验收 → 交付报告）
- 能力全开：读写、执行、测试、提交、分支、远端、Agent、审查、工具链配置

**边界（硬约束，不是提醒）**
> **只能改工作区内的文件。** 越界（工作区之外、系统目录、敏感路径）一律由沙箱直接拒绝，
> 甲方模式也不例外——`core/sandbox.py::jail()` 会抛 `路径越界`。

**交付物**：`DELIVERY.md`（验收清单/未完成项/建议）+ `TRACE.md`（需求→判据→证据→产物）。

---

## 二、开发者模式

**给谁用**：开发者。做细节化版本控制和代码写作时用。

**行为**
- `auto_approve=False`：**关键节点必须人工审核，不会自动放行**
- 五个关键节点（`KEY_NODES`）：

| 节点 | 什么时候触发 | 给人看什么 |
|---|---|---|
| `file.write` | 写盘前 | **unified diff**（改了什么，不是"要写文件"） |
| `git.commit` | 创建提交前 | 提交信息 + 涉及文件（版本控制关键点） |
| `git.push` | 推送/合并到远端前 | 目标远端/分支，force 会额外标注 |
| `remote.call` | 把代码发往远端模型前 | 任务号 + 包体大小 + "即将发送到 DeepSeek" |
| `deliver` | 收尾写交付物前 | 机械验收 X/Y + 收工原因 |

**审批怎么走（跨进程，这是关键）**
- 夜班可能跑在 CLI 进程，审批发生在浏览器界面——两边内存不共享，所以单据**落盘**在
  `<仓库根>/_logs/approvals/`：`<id>.json` 是待审单据，`<id>.decision.json` 是人的决定；
- 界面每 1.5 s 轮询 `GET /v1/approvals`，点「通过/拒绝」→ `POST /v1/approvals/{id}`；
- 终端里也能直接问（`SIXAGENT_APPROVAL=cli` 强制终端、`web` 强制走界面，默认 auto）。

**没人的时候**：**超时 600 秒按拒绝处理（fail-closed）**。
绝不因为"没人回答"就当成通过——这条是这套制度能不能信的底线。

**留下的证据**：每次请求/通过/拒绝/超时都写 `<工作区>/.sixcoder/audit.jsonl`，
事后能查"谁在什么时候放行了什么"。

## 三、只读模式

**给谁用**：拿到一份交付物，想先弄明白"它到底想干什么、哪里能改"。

**行为**
- 能力只有读：`probe.read / file.read / search.read / git.read / review.run / review.model`
- 没有 `file.write`、没有 `exec.run`、没有 `git.commit`、没有 `agent.run`
- 沙箱 `readonly`：写入直接抛错，命令只放行查看类（`ls / cat / git status / git log …`）
- 仍可跑**静态审查**与**模型语义比对**，给出改进建议（这两件事不写文件）

**典型用法**：`只读模式` → 打开某个 `projects/night*` → 看 `DELIVERY.md` / `TRACE.md` →
跑一次审查拿到改进清单 → 切回甲方/开发者模式去改。

## 四、三个模式的能力矩阵

| 能力 | 甲方模式 | 开发者模式 | 只读模式 |
|---|---|---|---|
| 读文件 / 检索 / git 查看 | ✅ | ✅ | ✅ |
| 静态审查 / 模型语义比对 | ✅ | ✅ | ✅ |
| 写文件 | ✅ 自动放行 | ✅ **需人批** | ❌ |
| 跑命令 / 跑测试 | ✅ | ✅ | ❌ |
| git 提交 / 分支 | ✅ 自动放行 | ✅ **需人批** | ❌ |
| git 远端（push/merge） | ✅ 自动放行 | ✅ **需人批** | ❌ |
| Agent 自动改代码 | ✅ | ✅ | ❌ |
| 发给远端模型 | ✅ 自动放行 | ✅ **需人批** | ❌ |
| 收尾交付 | ✅ 自动放行 | ✅ **需人批** | ❌ |

两条对三种模式都成立的铁律：
1. **文件只能写在工作区内**（沙箱牢笼，越界即拒）；
2. **判定权在引擎一侧**：模式只决定"允许调什么"，通过与否永远由机械判据说话（docs/16）。

## 五、怎么验证（不靠口头）

```powershell
cd prototype
python checks\check_modes.py       # 22 条断言，含 6 类反例
```

`check_modes.py` 覆盖：
- 名字必须是「甲方模式 / 开发者模式 / 只读模式」，默认是甲方模式，且没有"完全授权"残留；
- 能力矩阵（只读模式对 write/exec/commit/agent/remote 全部拒绝）；
- **甲方模式越界被拒**（`../escape.py`、`../../etc/passwd` 两条逃逸路径）；
- **开发者模式没人回答 → 超时拒绝**（并且确实等了，不是立刻放行）；
- **人工批准 → 放行**、**人工拒绝 → 该节点中止**；
- 审计日志确实落盘。

跨进程审批另有一条手工验证记录：CLI 进程抛 `needhuman` → 浏览器/接口 `POST /v1/approvals/{id}`
→ CLI 进程拿到 `approved` 继续（`_logs/approvals/` 落盘单据与决定文件）。
