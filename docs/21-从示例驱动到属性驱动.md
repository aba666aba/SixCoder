# 21 · 从"示例驱动"升级到"属性驱动"

这份文档只讲一件事：**"示例通过"不等于"函数对"**，以及我们用什么机械手段补上这个缺口。
所有数字都是本机实测（`python tools/measure_inspect.py --all -v` 可复现，只读、不调模型）。

## 一、示例驱动的窟窿（实证，不是理论）

`night2` 的 `report.py::summarize` 曾经是"验收通过"的一员：

- 契约里那一条示例过了：`summarize([{"age": 10, "email": "a@x.com"}])` ✓
- 独立验收（`tools/hq_verify.py`，19 条不共享代码的判据）也过了：19/19 ✓

但它照样崩：

```python
avg_age = round(sum(row.get("age", 0) for row in rows) / count, 1) if count > 0 else 0.0
```

`row.get("age", 0)` 只在**键不存在**时给 0。同一个工地的 `store.py::upsert`
是这样写库的：

```python
conn.execute("INSERT INTO people(...) VALUES(?,?,?,?,?)", (r.get("id"), ..., r.get("age"), ...))
```

`age` 缺失时写进去的是 **NULL**，读回来是 `None`，`sum()` 立刻 `TypeError`。
也就是说：**这个工具自己造出来的数据就能把它自己搞崩**，而示例和独立验收都看不见。

示例的问题不是"写得不好"，而是**它只有一条**。需求作者想到的那一条，永远是
最舒服的那一条。要抓这类错，只能从**类型**出发去造输入，而不是从需求作者的想象力出发。

## 二、属性驱动：边界矩阵

`core/props.py::boundary_checks` 按函数注解生成判据，不需要人写样例：

```python
BOUNDARY_SAMPLE = {
    "str":       ['""', '"   "', '"αβ"', '"x" * 1000'],
    "int":       ["0", "-1", "10 ** 6"],
    "list":      ["[]", "[1]"],
    "list[dict]": ["[]", '[{"age": 10}]', "[{}]", '[{"age": None}]', '[{"age": "10"}]',
                   "1000 行的 rows"],
    ...
}
```

生成策略是 one-at-a-time：先全部取"最小/空"，然后逐个参数换成病态值。
判定口径（关键，决定了误杀率）：

| 表现 | 判定 | 理由 |
|---|---|---|
| 抛 `ValueError/TypeError(业务层)/KeyError(业务层)` 等约定异常 | **合格** | 需求本来就要求"非法输入抛 ValueError" |
| 抛 `CRASH_EXC`（`AttributeError/KeyError/IndexError/TypeError/ZeroDivisionError/...`） | **不合格（硬）** | 这是"没想到"，不是"考虑过并拒绝" |
| 其余 | 合格 | |

这样 `clean_row` 对空串抛 `ValueError` 不会被误杀（它就该抛），
而 `summarize` 对 `None` 年龄崩掉必红。

**踩过的坑**：最初写成全局 `out[:10]`，一个模块里排在前面的函数把预算吃光，
后面的函数一条边界判据都拿不到 —— "边界矩阵"对它们等于不存在。
现在按函数截断（每函数最多 8 条），总量放到 80。

## 三、假绿的第二个漏洞：业务流"洗绿"

加完边界矩阵后，`night2/night3` 依然报 **8/8**。追下去是 `iterate.inspect` 里
跨模块业务流（e2e）那一段：它无条件把 `covers` 里的函数加回 `verified_names`，
**不看这个函数是不是已经被单函数判据判红**。

于是 `summarize` 在 `[]` 上 `ZeroDivisionError` 写得清清楚楚，却又被
"业务流跑通"补成绿色。

（顺带记一笔教训：第一版守卫加在了 `db_end2end` 那一段 —— 那一段本来就有守卫，
所以"修完还是 8/8"。改判据时先定位到**真正在写这个字段的那几行**再动手。）

修法是显式记账：`inspect` 为每个模块维护 `hard_failed` 集合，
e2e 只给"没有硬失败"的函数发信用。

### 中间那一列为什么变成了 7/7（一次误杀，必须留着）

第一版边界矩阵用一条**不一致的口径**把 `night4/night6` 的 `clean_row` 判红了：

- 新的边界判据（`robust`）说"业务异常算合格、崩溃才算不合格"；
- 老的 `call_ok`（按注解类型调用不报错）却把**任何**异常都算不合格。

于是 `clean_row({})` 抛 `ValueError`（它不肯收空行，这是设计选择）被当成错。
`docs/13` 的判据纪律要求"同一类证据只有一种口径"，所以把 `call_ok` 也改成同一口径
（只抓 `CRASH_EXC`），`night4/night6` 回到 7/7，`night7` 从 1/5 回到 2/5。

这条误杀值得记下来：**加严判据时，最容易犯的错不是漏判，是口径不一导致的误杀**，
而误杀会直接把系统推向"把对的函数改坏"。

## 四、变异门禁：从"记账"变成"门禁"

原来变异只写进交付报告，不影响验收 —— 等于没有。现在它是一道门，但阈值必须选对。

实测杀伤率（每个产物取 3 个变异体，只在本轮 diff 新增行上变异）：

| 产物 | 杀伤率 |
|---|---|
| `night2` | 2/3 = 67% |
| `night3` | 1/3 = 33% |
| `night6` | 1/3 = 33% |
| `night8` | 3/3 = 100% |

**结论：阈值不能设成"杀伤率 ≥ 50%"**。33% 那两次的实现其实是**对的**，只是测试写得弱；
一旦因为"测试弱"就判实现红，系统会把已经正确的函数反复重写（这件事在 night4 上真实发生过：
撤销信用后 8/8 掉到 3/8，6 轮原地打转）。

所以门禁只拦一种情况：**一个变异体都没杀掉**。那说明测试根本没碰到这段代码，
"测试通过"不含任何信息 —— 这正是假绿的定义。
参数 `SIXCODER_MUTATION_MIN`（默认 0.0）留给以后收紧用。

对应自检：`checks/check_bounds.py` 里两条反向用例 ——
"弱测试只要杀得掉一个就不判死"、"变异体全存活判红"。

## 五、可维护性硬指标（8 / 3 / 40）

三道纯 `ast`、零误判空间的指标：圈复杂度 ≤ 8、嵌套深度 ≤ 3、单函数行数 ≤ 40。

阈值不是拍出来的，先量现状：

| 指标 | 现有产物实测 |
|---|---|
| 圈复杂度最大值 | **10**（`night6 clean.py::clean_row`） |
| 单函数行数最大值 | **33** |

所以 40 行不会误杀任何现有正确产物；圈复杂度 8 只拦真正深嵌套的实现（上面那个 10 就被拦）。
`tools/gates.py::measure_quality` 可以只量不判，交付报告里给出数字；
`gate_quality_metrics` 才判红。

**这三道只上报、不剥夺单函数信用吗？** —— 不，它们**判红即剥夺**。理由：
"函数太长/太绕"是确定的、没有争议的，且修法唯一（拆小），不存在"其实它有道理"的情况。

## 六、哪些判据判红就剥夺信用，哪些只上报

这条界线必须写死，否则系统会自己在"严"和"松"之间漂移：

| 类别 | 判据 | 判红后 |
|---|---|---|
| 剥夺信用（硬门禁） | 语法、签名、桩、完整性、`call_eq`、`raises`、`keys`、`roundtrip`、`robust`（边界）、`call_ok`（只看崩溃）、`db_rows`、`duplicates`、`import_ok`、`dict_keys`、可维护性 | 该函数退出 `verified`，进入分诊派单 |
| 只上报（不剥夺） | `db_end2end` 失败（证不了是哪一步坏的）、`props.robust` 里 `hard=False` 的项（进 `advisories`）、`field_map`、依赖缺失、类型检查（advisory） | 写进交付报告与追溯矩阵，不撤销已有证据 |
| 门禁但只看"有没有信息" | 变异（零杀才拦）、断言率（模型 `assert` 恒 0） | 同上 |

`call_ok` 的例外要单独说清楚：它只抓崩溃型异常（`AttributeError/KeyError/...` 等 `CRASH_EXC`），
业务异常（`ValueError`）算合格 —— 理由见上一节那次误杀，`checks/check_bounds.py` 里有两条对应用例。

## 七、怎么验证这套东西是活的（不是猜的）

```bash
cd prototype
python checks/check_bounds.py     # 15 条，专测这四件事的两个方向
python tools/measure_inspect.py --all -v   # 真实产物的真账（只读）
```

`check_bounds.py` 把上面所有结论都钉成回归：

1. 四个函数都拿到边界判据（不再被总预算截断）
2. 边界判据默认是硬判据
3. `None` 年龄被边界矩阵判红，且反例给出具体输入
4. 补上确定的空值语义后转绿（不误杀正确写法）
5. 业务异常放行 / 崩溃异常判红（判定口径本身）
6. **业务流本身是通的**（否则第 7 条不成立）
7. **边界判红的 `summarize` 没被 e2e 重新算绿**（这条就是本次修的 bug）
8. 同一工地里 `clean`/`store` 仍然是绿的（没有一并误杀）
9. 圈复杂度超标判红 / 正常实现不误杀
10. 弱测试只要还能杀一个变异体就不判死 / 变异体全存活判红
11. 基线测试本来就是红的时候，变异结果被判为"无意义"（不许报成 100%）

## 七点五、交付报告里多了什么

`DELIVERY.md` 新增「代码质量与证据强度」一节，全部现场测量、跑不出来就写"跳过"：

- **已知会崩的输入**：边界判红的函数 + 具体反例（这是早上最该先看的一张表）；
- **可维护性**：是否在阈值内 + 最复杂的那一处（模块::函数、复杂度、嵌套、行数）；
- **测试有效性**：每个模块的变异杀伤率，零杀的打上"不能当证据用"。

这一节第一次跑出来就逮到一件旧报告从没说过的事：**`night8` 的三份测试文件
在未变异时就是红的**（`test_*` 自己跑不过）。如果不先跑基线就直接数变异体，
它们会全部"显得被杀死了"，报告上就是漂亮的 3/3 —— 这正是最危险的那种假绿。

## 七点六、门禁抓住之后，还要让它改得动

判据判红只是把问题变成工作单，改不改得动取决于**执行者有没有被告知这条约束**。
实测：夜班在第 7、8 轮两次正确诊断出 `summarize` 空输入除零，但产物仍是 7/8 ——
因为执行者的提示词里从来没有"空输入不许崩"这条铁律，它写完 `sum(x)/len(x)` 就觉得完事了。

所以补了两处（都属于"把门禁的约束前移给执行者"，而不是事后罚）：

1. `EXEC_PROMPT` 与 `dictfill.PROMPT` 各加一条铁律：空列表 / 缺键 / `None` 值不许崩，
   并点名三种常见崩法（除零、直接下标、`None + 1`）；
2. 字段级填充从"一遍"改成"最多两遍，第二遍带着上一次被判红的**具体反例**"，
   并且验收顺序变成 **契约判据 → 边界判据**，边界不过就直接回滚重填。
   （以前只验契约判据，所以 `avg_age = sum(...)/len(...)` 会当场通过，等下一轮才被边界抓。）

自检：`checks/check_dictfill.py` 现在会断言提示词里保留这两条（含"空输入"与"None"），
删掉就红 —— 免得以后为了省 token 又把它删了，把坑挖回来。

## 七点七、独立验收也补上了边界用例（我手写，不共享代码）

以前 `tools/hq_verify.py` 只有"正常路径"的 19 条，于是出现过很难看的一幕：
引擎 8/8、独立验收 19/19，而 `summarize` 在 `None` 年龄上崩。

现在加了 6 条**手写**边界用例（不 import 引擎任何模块，独立性不破）：

| 用例 | 期望 |
|---|---|
| `summarize([])` | `count == 0`，不崩 |
| `summarize([{"age": None, ...}])` | `count == 1`，不崩 |
| `summarize([{}])` | `count == 1`，不崩 |
| `clean_row({})` / `clean_row(只剩 age)` / `clean_row(age=None)` | 不崩（`ValueError` 算合格） |

判定口径和引擎侧**必须同一套**，否则两边会吵架：崩溃型异常不合格，`ValueError` 合格。
（第一版没写清这一条，`clean_row({"age": None})` 抛 `ValueError` 被我自己判红 ——
契约本来就要求"无法转整数抛 ValueError"，那是对的。这是同一个口径错误第三次出现，
所以现在两边都把它写成了显式的 `CRASH` 集合。）

同一批产物、新口径下的独立验收：

| 工地 | 旧（19 条） | 新（25 条） | 新增红的是什么 |
|---|---|---|---|
| `night2` | 19/19 | **24/25** | `summarize([{age:None}])` TypeError |
| `night3` | 19/19 | **22/25** | `summarize([])` ZeroDivisionError、`summarize(None)` TypeError、`clean_row(age=None)` AttributeError |
| `night8` | 12/19 | **15/25** | `parse_date` 缺 `datetime`（NameError）、`summarize` 恒返回空统计、`clean_row(age=None)` 崩 |

结论：**"引擎判红"和"我手写判红"现在指向同一批函数**。两个独立视角收敛到同一处，
才敢说这条判据不是自说自话。

### 两边不一致的地方，正好暴露契约表达不了的东西

`night6` 是反过来的例子：引擎 7/7 全绿，独立验收 20/23。差别在 `clean_row`：

```python
# 需求原文：clean_row(row: dict) -> dict：对 age/date/email 三个字段调用上面三个函数并返回新字典
# night6 实际返回：{'id': '', 'name': '', 'age': 30, 'email': 'a@b.com', 'birth': '2024-01-02'}
```

它把 `date` 改名成了 `birth`，还顺手塞了 `id/name`。我给 `clean_row` 手写的判据里
有一条"三个字段都要在、值要归一化"，所以它红了；而引擎的契约判据**表达不了这条** ——
需求没有写"返回的键必须与输入一致"，契约里也没有一条可机判的样例。

这正是 `docs/13` 说的那种情形：**需求没写清的部分，机制只能提示不能判**。
区别在于现在两边都把它摆到桌面上（引擎说"通过"，独立验收说"这条不符"），
而不是像以前那样两个都报绿。

## 七点八、两次 n=3 基准与一次受控 A/B（结论不好看，但必须照实写）

### 1）夜班基准 n=3：总分没涨，失败位置换了地方

| 基准 | 判据集 | 三次引擎验收 | 每函数可靠性 |
|---|---|---|---|
| 第一次（`13:15`） | 边界矩阵 + 防洗绿 | 7/8、7/8、7/8 | clean 四项 3/3、store 三项 3/3、**`summarize` 0/3** |
| 第二次（`13:47`） | 再加"空输入不许崩"提示词 + 字段级填充带反例重试 | 5/8、8/8、5/8 | clean 四项 3/3、**`summarize` 3/3**、**store 三项 1/3** |

两次的中位总分是 7/8 → 5/8，**总分变差了**。但看函数级就明白发生了什么：
`summarize` 从 0/3 变成 3/3（正好是我改的靶心），`store` 从 3/3 掉到 1/3
（两次抽到 `upsert() takes 1 positional argument` 这类签名错）。

结论只能这么写：**n=3 下这 3 分的差异是模型抽样方差，不能算作提示词改动的效果。**
真正的教训是方法论的 —— **"总分"这个指标被"哪个模块抽到手气差"完全支配**，
用它比较机制好坏是自欺；`docs/20` 说的"看每函数通过率"不是讲究，是唯一能读的读法。

### 2）受控 A/B：`summarize` 单函数的边界表现（同契约、同模型、六次调用）

`python tools/exp_dictfill.py --runs 3`（off = 普通符号编辑，on = 字段级填充）：

| 组 | 落盘 | 过契约判据 | **边界不崩** | 真走字段级填充 |
|---|---|---|---|---|
| off | 3/3 | 3/3 | **0/3** | 0/3 |
| on | 3/3 | 2/3 | **1/3** | 1/3 |

读法（三条，都不许美化）：

1. **普通路径 0/3 都栽在同一个地方**：`summarize([{}])` → `KeyError: 'age'`。
   7B 就是会写 `row['age']` 而不是 `row.get('age')`。加了提示词铁律也没治好 —— 这条只能靠机制，不能靠叮嘱。
2. **字段级填充现在会拒收**：on 组里只 1 次真正走了这条路，另外两次是"填出来的表达式
   在空输入上崩 → 判红 → 回滚重填 → 仍不行 → 退回普通路径"。
   也就是说字段级填充的收益从"看起来 3/3 通过"降到"1/3 真通过"，**这是变严，不是变差**：
   以前那条路会把"契约过、空输入崩"的代码当成成品交出去。
3. **唯一一次边界全绿，是走字段级填充成功的那次** —— 也就是"引擎给骨架 + 只填表达式 +
   边界验收"这条组合真的能做到，只是当前成功率只有 1/3。

### 2.5）把重试从 2 提到 3 并给"针对性改法"，结果没有变好（照实记）

第二轮 A/B（`SIXCODER_DICTFILL_TRIES=3` + `dictfill.advice()` 按异常类型给一句改法）：

| 组 | 过契约判据 | 边界不崩 | 真走字段级填充 |
|---|---|---|---|
| off | 2/3 | **0/3** | 0/3 |
| on | 1/3 | **0/3** | 0/3 |

比上一轮（on 边界 1/3）**更差**，而且三张单全部退回了普通路径。
n=3 下这个差别在噪声范围内，但它至少说明：**"多给几次 + 更清楚的改法"没有带来可见收益**，
反而每次失败要多烧 1~2 次模型调用（单次 33~40 s）。

所以现在的做法是**按证据分配重试预算**，而不是无条件加码：

- 首次实现（工作单里没有"边界"字样）→ 最多 2 次；
- 因为边界判红才重新派下来的单 → 3 次（这时多试才有意义）；
- 两种都能用 `SIXCODER_DICTFILL_TRIES` 覆盖。

这一条不写进"改进"清单，写进"试过但没用"清单。**试过但没用也要留证据**，
否则下次又会重走一遍。

### 3）下一步该做什么（按这次的证据排序）

| 优先级 | 做什么 | 为什么是它 |
|---|---|---|
| 1 | 给 `dict`-行函数加一条确定性改写：`row['k']` → `row.get('k')`，**仅当契约里该字段可缺省** | 这是当前 off=0/3 的唯一成因（`KeyError: 'age'`），且修法唯一；比叮嘱模型可靠 |
| 2 | `store` 的签名错走确定性修复（`upsert(conn)` 缺 `rows` 时按契约补参数） | 签名错不需要推理，`autofix` 里已有同类能力 |
| 3 | 契约里补"返回键必须与输入一致"这类可机判事实（对应 `night6` 的 `date→birth`） | 需要需求侧配合，属于"歧义只能提示"的边界 |
| ~~4~~ | ~~把字段级填充重试提到 3~4 次并给对比样例~~ | **已试，无收益（见 2.5）**，改为按证据分配预算 |

## 七点九、签名：一个"参数名就在契约里却没人用它"的洞

上一轮 n=3 基准三次里**两次**的失分来自同一个机械问题：

```
契约：upsert(conn, rows: list[dict]) -> int：按 id 覆盖写入，返回写入条数
产物：def upsert(conn: object) -> int: ...
报错：TypeError: upsert() takes 1 positional argument but 2 were given
```

回头看根因，不是"判据不够严"，而是**没人把契约里的签名交给修参数的那段代码**：

```python
# 改之前（iterate.execute_local）
fx = _autofix.fix_file(p, contract=order.get("acceptance") or "")
#        ↑ acceptance 长这样："契约判据通过（upsert）" —— 里面没有任何参数信息
```

`autofix` 里明明有一个按契约补参数的 libcst 转换器（`_FixParams`），因为拿到的"契约"
是一句自然语言，它一次都没被触发过。这是"机制存在但接线错了"的典型。

修法三件事，全部确定性、零模型调用：

| 改动 | 内容 |
|---|---|
| `autofix.spec_sigs()` | 从契约里抽"参数名 + 注解原文"，补参数时连注解一起补（以前补出来是裸名） |
| `iterate._sig_text()` | 用**解析出来的 Contract** 渲染精确签名，替代 acceptance 文案 |
| `iterate._signature_problem()` | 静态判两种"调用必炸"：契约声明的参数缺失 / 产物多出必填参数。多一个**可选**参数放行 |

`_signature_problem` 同时进了两个地方：
- `inspect`：逐函数判红并给归因（"签名缺参数：契约要求 upsert(conn, rows)，产物是 upsert(conn)，缺 rows"），
  以前同样的错只以端到端 `TypeError` 的形态出现，定位不到函数、也不剥夺信用；
- `execute_local`：写盘 + 确定性补参数后复核，还不对就当场退单，把窄证据带回去。

顺带补了 SQL 绑定形态（同一次基准的另一个真 bug）：

```python
cur.executemany(sql, [(r.get(k) for k in cols) for r in rows])   # 每行是生成器
# sqlite3: ProgrammingError: parameters are of unsupported type
```

`gate_db_rows` 现在用 ast 精确判这一种形态（外层推导 + 内层生成器），修法唯一（内层包 `tuple`）。
在 13 个历史产物上**零误报**，只命中 bench r1 那一个真 bug。

## 八、这一节的边界（不许含糊）

- 边界矩阵只能覆盖**注解写全了**的函数（`conn: object`、无注解的参数造不出样例），
  这类函数靠 `db_end2end` 兜，兜不住就是"未验"，不假装通过。
- `list[dict]` 的病态行（`{"age": None}`、`{"age": "10"}`、`[{}]`）是我们**猜的可疑输入**，
  不是全集的枚举。它抓到的是"明显没考虑过"的崩溃，抓不到"考虑了但考虑错了"。
  其中 `[{}]` 最严（空字典行连字段都没有），也是 7B 最容易栽的一条。按 `docs/13` 的纪律，
  这条"需要替甲方猜意图"的输入默认仍然硬判，但可以降级为提示（只影响这一条，别的照旧）：
  `SIXCODER_BOUNDARY_NO_EMPTY_DICT=1`。实测：即使降级，night2 的 `summarize` 照样在
  `[{"age": None}]` 上 TypeError —— 而 NULL 年龄是它自己的 `upsert` 造得出来的，所以降级救不了它，
  这一条不影响结论。
- 可维护性指标优化的是"以后还能改"，不直接提升这次的结果正确性；它属于质量底线，不是涨分项。
- 这次改动没有让任何一次夜班的总分上升（中位 7/8 → 5/8）。它的价值是：
  **已知会崩的函数不再被算成通过**，于是分诊会继续派单去修它 —— 修不修得动是下一步的事。
- 两次基准之间有 CPU 争用（我在同一台机器上跑验收脚本），耗时不可比，只比通过数。
