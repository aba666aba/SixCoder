# 05 闸门与验证流水线

> **本章是全项目最重要的一章。** 3B 模型的一切"质量"都来自这里：
> 模型不判断对错，闸门判断；模型不声明完成，闸门声明。
>
> 本篇定义 **G1–G6 基础闸门**（每节点必跑）。在它们之上还有 **Q1–Q10 质量闸门**
> （变异测试、覆盖率、依赖方向、复杂度、反逃避检测等），见 [12-质量最大化策略.md](./12-质量最大化策略.md) §5。
> 两者是叠加关系：G 保证"能跑"，Q 保证"值得交付"。

## 1. 六道闸门（按成本从低到高，任一不过即返回）

| # | 闸门 | 实现 | 通过判据 | 典型耗时 |
|---|---|---|---|---|
| G1 | 语法 | 语言解析器 / `py_compile` / `tsc --noEmit`（单文件） | 无解析错误 | < 0.2 s |
| G2 | 构建 | profile 的 build 命令（`mvn -q -o -DskipTests package` / `npm run build` / `python -m compileall`） | 退出码 0 | 3–40 s |
| G3 | 类型 | mypy / tsc / javac 严格模式 | 无 error | 2–15 s |
| G4 | Lint | `ruff --fix` / `eslint --fix` / `spotless:apply` | **自动修，不问模型** | 1–5 s |
| G5 | 测试 | 本节点绑定的测试（一个文件 / 一个用例类） | 全绿 | 2–30 s |
| G6 | 冒烟 | 起服务 + 健康检查 / CLI `--help` / compose `up -d` + 探活 | HTTP 200 或退出码 0 | 10–60 s |

### 1.1 闸门编排规则（`src/gates/runner.py`）

```python
def run_gates(node, workspace) -> GateReport:
    for gate in ordered_gates(node.kind):        # 按上表顺序，跳过与该节点无关的
        rep = gate.check(workspace)
        if not rep.ok:
            return GateReport(ok=False, failed=gate.name,
                              feedback=compact(rep, budget=700))   # ← 关键：压缩 feedback
    return GateReport(ok=True)
```

三条硬规则：

1. **失败即返，不跑完所有闸门**。语法都不过还去跑测试是浪费 3B 的采样预算。
2. **feedback ≤ 700 token**，见 §3。超预算等于没给。
3. **Lint 自动修复优先于报错**。格式问题不该占用模型的采样次数。

### 1.2 节点类型与闸门映射

| 节点 kind | 必过闸门 |
|---|---|
| `schema`（DDL/迁移） | G1 + DDL 可执行 + 可重放 |
| `iface`（接口签名） | G1 + G2 + G3 |
| `impl`（实现） | G1 + G2 + G3 + G5 |
| `test`（测试） | G1 + G5（必须红转绿；一直绿的测试视为无效测试，拒绝） |
| `config`（配置/打包） | G1 + G2 |
| `assembly`（集成装配） | G2 + G5 + G6 |

> "测试必须先红后绿"这条反幻觉机制很关键：3B 常写出恒真的测试（`assert True`，或断言自己刚写的实现）。规则是**先跑一次记录失败，再改实现让它变绿**；如果提交时测试本来就是绿的，说明测试没在验证任何东西，打回。

## 2. best-of-N：用小模型的算力换质量

3B 主力，单次通过率实测预期 50–65%；同一步骤采 3 次，用闸门当选器：

```python
for i in range(N):                      # N=3（3B）/ N=2（7B）
    patch = llm.generate(prompt, temperature=jitter(i))   # 0.15/0.25/0.35
    rep = run_gates(apply_dry(patch), workspace)
    if rep.ok:
        commit(patch); return SUCCESS
    failures.append(rep)
# 全部失败 → 取"失败得最少"的一次作为进入升级阶梯的输入
```

为什么这在你的硬件上是最优交易：3B 一次补丁约 **15–20 s**，3 次 ≈ 1 分钟；而 7B 一次要 **60–90 s** 且上下文稍长就更慢。同样的墙钟时间，**3 次 3B + 闸门 优于 1 次 7B**。

注意 jitter：三次不能用同一 temperature，否则三次输出高度相似（3B 尤其明显）。用 0.15 / 0.25 / 0.35 并打乱 seed。

## 3. 结构化反馈：把日志变成模型能用的东西

`src/gates/feedback.py` 的输出格式（硬预算 700 token）：

```
【失败闸门】G2 构建
【错误】Cannot find symbol: method setTimeout(int)  —  src/service/JobService.java:47
【上下文】
  43 | public void run() {
  44 |     scheduler.schedule(this);
  45 | }
  ...
  47 |     executor.setTimeout(30);
【提示】JobService 中是否已导入 java.util.concurrent.ScheduledExecutorService？
```

规则：

- **只取第一条错误**（编译器第一条通常就是根因，后面的多是级联噪声）
- 附 **±3 行代码 + 行号**
- 不贴整段堆栈；堆栈只在无错误信息时贴最内层 3 帧
- **不做推测性建议**（"你可能想用 X"）—— 3B 会照抄建议而不是修根因；只给事实（"该方法签名在 `Iface.java:12` 定义为 `setTimeout(long)`"）

## 4. 评审为什么不用 LLM（推翻 SixAgent 的设计）

SixAgent 的 `ReviewerService` 让 LLM 输出 P0/P1/P2 分级问题清单，然后 P0 触发修复。在 7B/30B 上勉强可用，在 3B 上是**负价值**：

| 维度 | LLM 评审 | 闸门 |
|---|---|---|
| 3B 可靠性 | 低（几乎总说"代码质量良好，建议加注释"） | 100%（退出码不会撒谎） |
| 成本 | 一次完整文件评审 ≈ 2K token ≈ 40 s | 编译 3 s |
| 可复现 | 否 | 是 |
| 能抓的缺陷 | 风格、命名、潜在空指针（靠猜） | 编译错、类型错、测试失败、启动失败（靠事实） |

**替代方案**：LLM 只做两件它擅长的事——
1. **需求 → 规格/契约**（`plan` 模式，7B）
2. **闸门失败后的定向修复**（`repair` 模式，3B，输入是窄反馈）

"评审"这个角色被拆成"静态闸门 + 测试"。

## 6. 闸门的性能预算（4GB 卡上的时间账）

单节点目标：**≤ 3 分钟**（含 3 次采样 + 闸门 + 重试一次）。

| 阶段 | 预算 | 说明 |
|---|---|---|
| 上下文装配 | 0.5 s | 缓存命中时近乎 0 |
| 生成（3B，600 tok） | 15–20 s | 主力 |
| G1–G3 + G5 | 5–40 s | 取决于 profile；Java 构建较慢，用 `-o` 离线 + 增量 |
| 失败重试（平均 0.6 次） | +20 s | — |
| 合计（均值） | **~90 s** | 100 节点 ≈ 2.5 小时纯计算 |

优化优先级（当时间不够时按此顺序做）：

1. **语义缓存**（同一节点重跑直接命中）
2. **增量构建**（Maven/Gradle 增量、`ruff` 只查改动文件）
3. **闸门降级**（`impl` 节点先跑 G1+G5，全节点 G2 放到集成阶段）
4. 上下文预算收紧（把 ④ 规约摘要从 400 压到 200）
