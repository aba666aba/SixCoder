# 13 判定权分离与自认可防护

> **自认可是本项目最危险的失效模式，因为它不报错。**
> 它会产出：通过率虚高、报告全绿、交付错误的产品。
> 本章做三件事：**审计已有设计里的自认可点**、**给出唯一可靠的不变式**、**把"谁有权判定什么"变成可审计的机制**。

---

## 1. 先回答：会出现吗？

**会。** 已有设计中存在 5 处，按危害排序：

| # | 位置 | 自认可形式 | 危害 |
|---|---|---|---|
| S1 | 测试节点（G5） | **模型写测试来判定模型写的实现** | 致命：写个恒真测试就全绿了 |
| S2 | 规格链（07 §3） | 模型写规格 → 模型实现 → 模型生成测试 → **错得很自洽** | 致命：全绿，但做的是用户没要的东西 |
| S3 | 候选选优（12 §4-M2） | 7B 判别 3B 的候选（同家族、同训练数据、同偏见） | 高：判别结果可能系统性偏好某类写法 |
| S4 | 强制精修轮（12 §4-M1） | 模型"自我审查"自己的代码 | 中：只能发现它自己知道的问题 |
| S5 | 状态自述 | 模型在文本里说"已完成/已修复" | 中：若任何代码解析了这句话，状态就假了 |

另有两处隐蔽的（S6/S7）：

| # | 位置 | 形式 |
|---|---|---|
| S6 | 覆盖率（Q5） | 模型写"执行到但不反证"的测试刷行覆盖率 |
| S7 | 经验库（12 §4-M5） | 若某次"成功"是靠作弊过的，修复模式会被学走并放大 |

---

## 2. 根本原因与唯一可靠的不变式

**根本原因：同一主体同时掌握"生成权"和"判定权"。**

四条不变式（Invariants），任何实现都必须满足，代码评审以此为准：

### I1　状态只由闸门产出，永不由模型文本产出
模型的任何文字输出（"已完成"、"修复成功"、"Looks good"）**只能进轨迹日志，不能进状态机**。
`nodes.status` 的唯一写入者是 `tasks/runner.py`，依据是 `gate_runs` 记录。

### I2　判定者必须与生成者不同源
判定强度排序（自上而下，越上越可信）：

```
确定性程序（退出码/断言/编译器/静态分析/变异测试）
   > 与生成者无关的代码路径（模板生成的测试、属性测试）
      > 不同模型（不同家族，且仅做"提示"不做"判定"）
         > 同模型不同提示（禁用）
            > 同模型自述（禁止作为判定依据）
```

### I3　自洽链必须被外部锚点打断
凡是"模型 A 定义的、模型 A 实现的、模型 A 验证的"闭环，必须在**至少一处**接上锚点：
- 需求**原文**（规格项必须能回指到原文字句）
- **人工签核**（架构一次、交付一次）
- **变异测试**（测试必须能在实现被破坏时失败）

### I4　没有反证的"通过"不算通过
一个测试只有**在实现被变异时会失败**，才算验证了东西（12 §4-M3）。
一个功能只有**在缺失时对应测试会红**，才算被测试覆盖。

---

## 3. 判定权矩阵（谁有权判定什么）

| 结论 | **唯一有权判定者** | 模型有无发言权 |
|---|---|---|
| 语法正确 | 解析器 | 无 |
| 能构建 | 构建命令退出码 | 无 |
| 类型正确 | 类型检查器 | 无 |
| 测试通过 | 测试框架退出码 | 无 |
| **测试有效** | **变异测试杀死率** | 无 |
| 代码质量达标 | 静态分析阈值（复杂度/重复/依赖方向） | 无 |
| 需求已实现 | 需求原文编号 → 测试引用映射 + 人工签核 | 仅能提议映射，不能判定 |
| 补丁最小 | `git diff --numstat` | 无 |
| 可交付 | D1–D8 脚本全绿 | 无 |
| 选型正确 | 打分函数（11 §1.2） | 仅提供技术线索关键词 |
| 任务完成 | 上述全部 AND | **无判定权** |

**每一行"模型有无发言权"为空白的，就是一条红线。** 代码评审时用这张表逐项对。

## 4. 逐点修补

### S1（模型写测试判自己实现）→ 四道组合

| 措施 | 为什么能治 |
|---|---|
| **测试由模板生成骨架**（不是自由创作） | 测试结构来自 profile 模板：用例名、输入、期望值槽位由契约填，模型只填具体值 |
| **先红后绿**（强制） | 测试提交时必须失败；绿了视为无效测试，拒绝 |
| **变异测试**（Q6） | 空洞测试杀不死变异体；这是唯一能**量化**"测试有没有在验证"的机制 |
| **断言有效性检查** | AST 检查：每个 test ≥1 个断言、断言非常量恒真（`assertTrue(true)` / `assertEquals(x, x)` 拒绝）、异常路径测试存在 |

### S2（规格→实现→测试全模型自洽）→ **双轨规格交叉验证**

这是本章新增的核心机制（`src/tasks/spec.py`）：

```
轨 A：需求原文 ──(3B/7B)──▶ 规格 A（实体/字段/规则/接口）
轨 B：规格 A ──(不同 prompt + 尽量不同模型)──▶ 反向复述的需求 B
                        │
                 diff(需求原文, 需求 B)
                        │
        ┌───────────────┴───────────────┐
   差异 = 0 或可忽略               差异非 0
        │                               │
   进入任务图                  生成【假设清单】→ 用户确认（1 次，不是每步）
```

**外加一条硬规则**：规格里每一项必须带 `source_span`（需求原文中的对应字符区间）。

```json
{"kind":"field","name":"stock","type":"int",
 "source_span":"[42,47] \"库存\"",        // ← 指不到原文的项视为"模型臆造"
 "derived":false}
```

- `source_span` 为空且 `derived=false` → **视为臆造，直接剔除**（不进规格、不进测试）
- `derived=true` → 必须写明推导链与风险，进假设清单让用户确认

这条规则的价值：它把"模型补充的合理猜测"从暗处拉到明处，并强制用户点一次头。**绝大多数"做错了但全绿"的项目，死在这里。**

### S3（7B 判别 3B 候选）→ 降级为"提议"，且优先用确定性判别

| 优先级 | 判别方式 | 说明 |
|---|---|---|
| 1 | 闸门本身 | 能区分就用闸门，不用模型 |
| 2 | **确定性 checklist**（12 §4-M6） | 契约要点覆盖、新依赖、diff 大小、无关改动 |
| 3 | **差分探测** | 对两个候选各生成 3 个"边界输入"的期望行为（由契约确定性推导），看哪个更符合 |
| 4（lower） | 7B pairwise | **只在 1–3 全部无法区分时使用**；其结果只能"选优"，**不能推翻任何闸门失败**，且必须记入 `evidence_kind=model_text`（不计入通过证据） |

### S4（模型自我审查）→ 限定为"执行清单"，不是"评价代码"

已有设计（12 §4-M1）本来就是这样，这里固化为规则：

- 精修轮的输入**只能是确定性检查输出**（未使用 import、CCN>10 的函数、清单指出的缺失分支）
- 模型**不得**自行新增"我觉得还应该改…"的项；生成的补丁若超出清单范围 → 打回
- 精修后必须仍全绿，且 diff 不得超出预算

### S5（状态自述）→ I1 + schema 强制

`gate_runs.evidence_kind` 枚举固定：

```
exit_code | assertion | mutation | static_rule | human | model_text
```

规则：
- **`model_text` 永不计入通过**
- 交付报告必须给出 `model_text` 占比，**该值必须为 0**；非 0 即为引擎 bug（有单测守着）

### S6（覆盖率刷行）→ 覆盖率降级为"参考指标"

| 指标 | 地位 |
|---|---|
| 行/分支覆盖率 | 参考（不达标要说明原因） |
| **变异杀死率** | **准入门槛**（改动文件 ≥60%） |
| 断言密度（断言数/测试数） | 静态检查（≥1，且非恒真） |

### S7（经验库放大作弊）→ 入库条件严格化

一条经验进库必须同时满足：
1. 闸门全绿
2. **`anti_cheat` 全过**
3. **变异杀死率达标**（证明测试真的在验证）
4. 该经验被复用 ≥3 次且成功率 ≥0.7（否则降权）

不满足的一律不进库。宁可库小，不可库脏——脏库比没有库更糟。

## 5. 人工签核不能流于形式

两处签核（`approvals` 表：`stage = spec | delivery`）是 I3 的最后一道锚点，必须防"无脑点确定"：

| 规则 | 实现 |
|---|---|
| 签核界面必须展示三样东西 | ① 假设清单（含 `source_span`）② 需求→测试映射 ③ NEEDS_HUMAN 清单 |
| 三样东西必须被**看过**才能签 | 每块折叠区展开后才启用按钮；或勾选"我已核对映射表" |
| 签核内容哈希入库 | `approvals.content_sha256`，事后可证明"签的是哪一版" |
| 签核后发现需求偏差 | 冻结该 task 的交付资格，必须回滚到 spec 阶段 |

## 6. 一个可审计的硬指标：自认可率

给引擎加一条全局指标，写进每次的交付报告：

```
模型断言率 = 由 model_text 支撑的通过结论数 / 全部通过结论数      ← 必须 = 0
自派生规格率 = 无 source_span 的规格项数 / 规格项总数            ← 必须 = 0
测试空洞率  = 杀死率 < 阈值 的测试文件数 / 测试文件总数          ← 应 < 10%
```

三个数字都是**确定性计算**，不依赖模型。它们是本项目"质量"能不能被相信的唯一凭据。

---

## 7. 代价：通过率会下降

消除自认可后，指标一定变差——**这是设计正确的信号，不是退步**。

| 指标 | 存在自认可时（虚高） | 消除后（真实） |
|---|---|---|
| 一次通过率（3B × N=3） | 78–86% | **65–75%** |
| 变异杀死率 | 25–40%（没人看） | 45–60%（准入门槛） |
| `needs_human` 率 | 3–8%（假低） | **15–25%（真实）** |
| 交付后返工率 | 高（交付了错的东西） | 低 |

**接受这个代价是本项目成立的前提。** 一个 65% 的真实通过率，比一个 86% 的虚假通过率有用得多——因为前者你知道该看哪里，后者你不知道。

## 9. 一句话总结

> 模型可以**生成**任何东西，但**无权判定**任何东西。
> 凡是"模型说它对"的地方，必须换成一个**能在它错的时候失败的检查**。
> 换不掉的，就交给人在两处签核，并明确写进 `NEEDS_HUMAN`。

## 10. 姊妹问题：判定权分离 → 操作权分离

判定权解决"谁说了算"，**操作权**解决"谁有权动手"。两者是同一条原则的两个面：

| 操作 | 人类通道（UI 按键 / CLI） | 模型通道（Agent） | 理由 |
|---|---|---|---|
| 读文件 / 检索 | ✅ | ✅ | 无副作用 |
| 写文件 / 补丁 | ✅ | ✅（沙箱牢笼 + 备份） | 有副作用但可撤销 |
| 执行构建 / 测试 | ✅ | ✅（白名单） | 只读性命令 |
| `git commit` | ✅ | ✅（仅引擎快照） | 可追溯 |
| `git push` / `fetch` / `pull` | ✅ | ❌ 禁止 | **不可逆、影响他人** |
| `git remote` / `config` | ✅ | ❌ 禁止 | 凭据与远端配置 |
| `git reset --hard` / `filter-branch` | ❌ 也不给人类（提供 `checkout --` 与沙箱撤销替代） | ❌ | 破坏性且难恢复 |
| `git push --force` | ⚠️ 需显式，单独记高危审计 | ❌ | 强破坏 |

三条落地规则：

1. **权限跟着"发起者"走，不跟着"代码路径"走**：不是"这个函数危险所以谁都不能用"，而是"模型发起时禁止，人类发起时允许并留痕"。
2. **危险操作必须显式 + 可审计**：`push --force` 走 `--force-with-lease`，并在 `.sixcoder/audit.jsonl` 写 `human:PUSH_FORCE` 记录。
3. **删除/覆盖类操作一律给"可逆替代"**：`reset --hard` → `checkout -- <path>`（单文件）或沙箱写盘日志回滚（连未提交也能撤）。

### 10.1 三档权限模式（已落地）

"双通道"太粗，实际用起来还需要**用户可选的粒度**。系统改成 3 档 × 13 项 capability：

| 模式 | capability 数 | 语义 |
|---|---|---|
| `readonly` 只读勘察 | 5 | 只看不改；审查也只跑确定性规则（模型比对关闭） |
| `edit` 安全编辑（默认） | 12 | Agent 改代码、跑测试、本地提交、分支；**禁远端** |
| `full` 完全授权 | 13 | + 远端同步（fetch/pull/push/merge/设置远端） |

关键实现约束（三条闸口用**同一个 capability 定义**，避免漂移）：

```
core/permissions.py:  CAPS + MODES + require(cap)
HTTP:  _guard(cap) → 403 + "当前模式「X」不允许该操作…请切换到「Y」"
CLI:   _need(cap)  → 退出码 3 + 同一句话
UI:    :disabled="!can(cap)" + 一行说明该开哪个模式
```

**为什么拒绝消息必须带"该开哪个模式"**：权限拒绝是用户会遇到的高频挫败点。只说"403"会让人以为是 bug；
说"需要完全授权模式"才是可操作的。这条和 §3 判定权矩阵的精神一致——**每条拒绝都要指向一条可行路径**。

> 实测：`readonly` 下 push/agent/bash 全部 403，`tool list`（只读）正常；
> `edit` 下 push 被拒、commit 可用；`full` 下 push 成功。同一套代码，三档粒度。

> 实测：模型通道 8 类越权尝试（curl / push / pip / powershell / reset --hard / 越界读 / .env / git config）全部被拒；
> 人类通道在同一台机器上完成了 init → commit → push → pull → merge → sync 全流程。
> **同一套代码，两种权限，靠发起者区分** —— 这比一刀切的禁列表既安全又好用。
