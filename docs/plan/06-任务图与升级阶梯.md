# 06 任务图与升级阶梯

> 本章解决两个"看起来不是问题、实际致命"的点：
> **① 一次运行几小时，中途必然出岔子 → 必须可断点续跑、不重复劳动。**
> **② 小模型必然失败若干次 → 失败必须升级而不是重试，且失败信息必须被记住。**

---

## 1. 数据模型（`src/tasks/schema.sql`，SQLite）

```sql
-- 一次需求 = 一个 task
CREATE TABLE tasks (
  id            TEXT PRIMARY KEY,          -- t-20261010-a1b2
  requirement   TEXT NOT NULL,             -- 原始需求
  profile_id    TEXT NOT NULL,             -- spring-vue / python-fastapi
  status        TEXT NOT NULL,             -- spec|building|verifying|done|needs_human|failed
  workspace     TEXT NOT NULL,             -- workspaces/t-.../  独立仓库
  model_tier    TEXT NOT NULL DEFAULT 'main',  -- main(3B) | strong(7B)
  spec_json     TEXT,                      -- 规格化结果（实体/字段/角色/约束）
  created_at    TEXT, updated_at TEXT,
  metrics_json  TEXT                       -- token/时长/重试次数/终止原因
);

-- 任务图节点：可独立验证的最小工作单元
CREATE TABLE nodes (
  id            TEXT PRIMARY KEY,
  task_id       TEXT NOT NULL REFERENCES tasks(id),
  seq           INTEGER NOT NULL,          -- 稳定性排序（用于确定性重放）
  kind          TEXT NOT NULL,             -- schema|iface|impl|test|config|assembly
  path          TEXT,                      -- 目标文件（相对 workspace）
  contract      TEXT NOT NULL,             -- 人话契约（进 Prompt 的 ①）
  deps_json     TEXT NOT NULL DEFAULT '[]',-- 依赖节点 id 数组
  status        TEXT NOT NULL DEFAULT 'pending', -- pending|ready|running|blocked|done|needs_human
  attempts      INTEGER NOT NULL DEFAULT 0,
  escalate_lvl  INTEGER NOT NULL DEFAULT 0,-- 0-7，见 §4
  last_error    TEXT,                      -- 最近一次窄反馈（升级时进 Prompt ⑤）
  snapshot_commit TEXT                     -- 本节点成功后的 git 快照
);

-- 每次闸门运行的记录（可回归、可归因）
CREATE TABLE gate_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  node_id TEXT NOT NULL, gate TEXT NOT NULL,
  ok INTEGER NOT NULL, elapsed_ms INTEGER,
  feedback TEXT, created_at TEXT,
  -- ★ 判定权分离（见 13 §4-S5）：通过结论必须有确定性证据
  evidence_kind TEXT NOT NULL,      -- exit_code|assertion|mutation|static_rule|human|model_text
  evidence_ref  TEXT,               -- 退出码/断言名/变异体 id/规则 id/签核记录 id
  CHECK (evidence_kind IN ('exit_code','assertion','mutation','static_rule','human','model_text'))
);
-- 不变式：nodes.status 只允许由 gate_runs 中 evidence_kind != 'model_text' 的记录推进；
--        'model_text' 仅作轨迹留痕，永不计入通过。

-- 产物索引（交付报告与前端差异页的数据源）
CREATE TABLE artifacts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id TEXT NOT NULL, path TEXT NOT NULL,
  kind TEXT, sha256 TEXT, bytes INTEGER, created_at TEXT
);

-- 人工闸门（只两处：架构签核、交付签核）
CREATE TABLE approvals (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id TEXT NOT NULL, stage TEXT NOT NULL,   -- spec | delivery
  decision TEXT, note TEXT, decided_at TEXT
);
```

> 迁移策略：`PRAGMA user_version` + 编号 SQL（`migrations/001_init.sql`、`002_*.sql`），不引 Flyway。

## 2. 节点展开（确定性，不用模型）

展开规则由 profile 的模板结构决定，**不让模型自由规划**：

```
需求 + spec_json + profile
   │
   ├── 每个实体 → iface(签名) → schema(DDL/迁移) → impl(service/repo) → impl(controller/router) → test
   ├── 认证/通用能力（能力清单已声明） → 直接套模板 → config 节点
   └── 收尾 → assembly(main/配置/DI 装配) + config(Dockerfile/compose/CI) + README 生成
```

展开时必须满足的**工作单元上限**（硬约束，超出即再拆）：

| 约束 | 值 | 校验方式 |
|---|---|---|
| 单节点改 1 个文件 | 1 | 展开后校验 |
| 单节点新增/修改 ≤ 120 行 | 120 | 生成后统计 diff |
| 单节点绑定 ≤ 1 个测试用例类/文件 | 1 | 展开后校验 |
| 单节点上下文 ≤ 3,500 token | 3500 | 生成前预算 |

> 这条约束是本项目"3B 能用"的根本原因，等价于把一次开放搜索换成 N 次受限搜索。**扩产靠节点数变多，不靠节点变大。**

## 3. 主循环（`src/tasks/runner.py`）

```python
def run_task(task):
    spec = maybe_spec(task)                 # 阶段 A：规格化（7B，一次）
    ask_approval(task, "spec")              # 人工闸门 1：架构签核
    graph = expand(task, spec)              # 阶段 B：确定性展开
    while True:
        node = next_ready(graph)            # 依赖全 done 且 status=pending
        if node is None: break
        run_node(node)                      # 阶段 C：生成→闸门→提交
    run_assembly(graph)                     # 阶段 D：装配 + 全量闸门 + 冒烟
    report = delivery_check(task)           # 阶段 E：8 条交付门禁
    ask_approval(task, "delivery")          # 人工闸门 2：交付签核
```

### 3.1 `run_node` 的伪码（含快照与升级）

```python
def run_node(node):
    for attempt in range(node.max_attempts):          # 默认 7（对应 7 级阶梯）
        ctx   = assemble_context(node, budget=3500)   # 04 章的四件套
        patch = generate(node, ctx)                   # 3B/7B + best-of-N
        rep   = run_gates(dry_apply(patch), workspace)
        record_gates(node, rep)
        if rep.ok:
            commit = git_snapshot(node)               # git add <本节点路径> && commit
            node.snapshot_commit = commit
            mark_done(node); return
        node.last_error = compact(rep.feedback)       # 记住失败，进下一次上下文
        escalate(node)                                # 见 §4，改变策略
    mark_needs_human(node, node.last_error)
```

### 3.2 Git 快照规则（对 SixAgent 破坏性做法的修正）

| 规则 | 反例（SixAgent） |
|---|---|
| `git add` **只加本节点涉及的文件**，不加 `-A` | `GitService:56` 用 `git add -A`，把用户所有未提交改动卷进 AI 提交 |
| 失败回滚用 `git checkout -- <本节点文件>`，**不碰其他文件** | `GitService:113` `git reset --hard <hash>`，抹掉用户与他节点成果 |
| 每个任务独立 `workspaces/<task_id>/` 仓库副本 | `TraceController` 不接 `workingDir`，操作落到 `user.dir/output` |
| 提交身份用仓库级 `git -c user.name=... commit` 显式传入 | 依赖全局配置 |

## 4. 七级升级阶梯（`src/tasks/escalate.py`）

**绝不原样重试同一提示词。** 每失败一次，改变的是**策略**，不只是温度：

| 级 | 动作 | 具体改动 | 期望 |
|---|---|---|---|
| L1 | 重采样 | 换 temperature/seed（best-of-N 已在做） | 抖动命中 |
| L2 | 窄反馈重试 | 把 `last_error`（一条错误 + 片段）注入 prompt | 定向修复 |
| L3 | **缩小步长** | 节点拆分：只实现 happy path / 只改一个方法 / 测试先降为一例 | 搜索空间减半 |
| L4 | **plan-first** | 先让 7B 输出 JSON 步骤（不写码），再按步骤逐条执行 | 结构化 |
| L5 | **升级模型** | 换 7B（此时上下文已 ≤2K，prefill 可控） | 智力补齐 |
| L6 | **模板兜底** | 用 profile 模板生成该文件的骨架实现，函数体留 `raise NotImplementedError` + `NEEDS_HUMAN: <原因>` | 保住可编译 |
| L7 | **挂起** | 标记 `needs_human`，**继续跑其他独立节点**，最后集中人工 | 不阻塞全局 |

规则细节：

- L3 拆分产生的新节点**继承**父节点的 `last_error`，避免重复踩坑。
- L5 是唯一使用 7B 的路径，且必须**串行且独占**（4GB 卡换模型有 ~20 s 冷启动，走队列插队）。
- L6 产出的 `NEEDS_HUMAN` 必须有明确原因和所需人工动作（"需决定 Redis 连接配置来源"），不是"我不行"。
- 阶梯是**每个节点独立**的；一个节点到 L7 不影响其他节点。

## 5. 断点续跑与幂等

| 场景 | 行为 |
|---|---|
| 进程被杀 / 断电 | 重启后按 `nodes.status` 恢复：`running` → 退回 `pending`（并从快照恢复该文件），`done` 跳过 |
| 同一步骤重复执行 | 先查 `artifacts.sha256`：若目标文件已是期望内容，直接 `done`（幂等） |
| 用户改了目标仓库 | 检测工作区 `git status` 非空 → **暂停并提示**，不覆盖用户改动 |
| 换模型重跑 | `tasks.model_tier` 记录；重跑同 task 时默认沿用，可显式覆盖 |
| 交付失败后重跑 | 只重跑失败的 `delivery` 检查项，不重跑已 done 节点 |

**可复现性**：`nodes.seq` 是稳定的，同一 task 在同样模型/温度下重跑应得到**同序**的执行路径；生成结果仍可能不同（LLM 非确定性），但**闸门结论可复现**——这才是我们能承诺的东西。

## 6. 观测与报告（复用 `src/observability/`）

每次 task 结束产出（`workspaces/<task_id>/report.md` + JSON）：

| 段 | 内容 |
|---|---|
| 摘要 | 节点总数 / done / needs_human / 各级 upgrade 次数 / 总 token / 墙钟 |
| 需求→测试映射 | 每条需求 → 覆盖它的测试文件:用例名 |
| 闸门统计 | 各闸门失败次数（哪个闸门最常拦下，就是下一轮优化的地方） |
| NEEDS_HUMAN 清单 | 节点 / 原因 / 所需人工动作 / 当前占位实现 |
| 模型使用分布 | 3B 调用次数、7B 调用次数、缓存命中率 |
| 复现命令 | 一条命令重跑该 task |

这些指标不是装饰：**闸门失败分布直接告诉你该收紧哪个模板、该给哪个 profile 补能力**。
