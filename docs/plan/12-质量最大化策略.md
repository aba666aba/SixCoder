# 12 质量最大化策略

> 目标：在 **3B 主力 + 4GB 显存**的硬约束下，把最终代码质量推到这套硬件能达到的上限。
> 核心论点：**模型质量 = 单步能力 × 验证强度 × 尝试次数 × 结构性约束**。
> 前两项我们能靠设计放大，第四项能直接兜底。所以"最高质量"不是靠更聪明的模型，而是把这四个乘数都拉满。
>
> ⚠️ **本章所有质量机制都建立在一个前提上：判定权必须与生成权分离。**
> 否则本章等于在给"模型自认可"做包装——详见 [13-判定权分离与自认可防护.md](./13-判定权分离与自认可防护.md)。
> 尤其注意：`model_text` 类证据永不计入通过（13 §4-S5），变异测试是测试有效性的唯一量化准入（13 §4-S1）。

## 1. 质量的可加分解（先定义，才能度量与提升）

| 维度 | 权重 | 由什么保证 **（机制）** | 判定方式 | 目标值 |
|---|---|---|---|---|
| 正确性 | 30% | 契约 + 闸门 + 测试 | 构建/类型/测试退出码 | 100% 通过 |
| 测试强度 | 20% | 先红后绿 + **变异测试** + 属性测试 + 负向测试强制 | 变异杀死率 / 分支覆盖 | 杀死率 ≥ 60%，分支覆盖 ≥ 70% |
| 一致性 | 15% | 模板 + 规约 + 静态检查 + 依赖方向规则 | 风格违规数 / 分层违规数 | 0 |
| 最小性 | 15% | 补丁预算 + 无关改动检测 | `git diff --numstat` | ≤ 预算且无关改动 0 |
| 安全性 | 10% | 密钥扫描 + 注入模式检查 + 依赖漏洞 | 扫描命中数 | 0 |
| 可维护性 | 10% | 复杂度/长度阈值 + 命名检查 + 注释覆盖 | 违规函数数 | 0 |

**加权和 = 本项目的"质量分"**，写进每次任务的交付报告，可跨版本对比。
不是为了好看——**它把"质量"变成了可以回归的东西**：改了引擎，跑同一批需求，质量分不该降。

## 2. 三根杠杆与上限

```
最终质量 Q  ≈  f(单步任务规模 S, 验证强度 V, 尝试次数 N, 结构约束 C)
              S 越大 → 崩塌（3B 在 >120 行的单元上质量断崖）
              V 越强 → 崩塌被捕获（构建 < 测试 < 变异测试 < 属性测试）
              N 越大 → 命中概率提升（但有边际递减）
              C 越强 → 输出更可预测（模板/契约把"创作"变成"填空"）
```

| 杠杆 | 手段 | 本项目的取值 |
|---|---|---|
| S（单元规模） | 单节点 ≤1 文件 / ≤120 行 / 1 测试契约 | 04 §2、06 §2 |
| V（验证强度） | 6 道闸门 → 升级为 **10 道质量闸门**（§5） | 本文 §5 |
| N（尝试次数） | best-of-3 3B → 难度高时 best-of-5 | 本文 §3 |
| C（结构约束） | 契约先行 + 模板 + Profile | 07 §3 |

**不要指望第四项以外的东西。** 换模型（3B→7B）只是把 S 的上限从 120 行抬到 ~200 行，不解决验证与结构问题。

## 3. 测试时算力分配器（把 N 花在刀刃上）

均分预算是最蠢的做法：给"加一个 getter"采 5 次是浪费，给"实现跨表事务"采 1 次是赌博。

### 3.1 难度先验（确定性打分，不调模型）

```python
def difficulty(node, history) -> float:      # 0..1
    d = 0.0
    d += 0.25 * (node.kind in {"impl", "assembly"})        # 实现类最难
    d += 0.20 * (len(node.deps) >= 2)                      # 依赖多
    d += 0.15 * (node.contract_has_business_rule)           # 含业务规则/边界条件
    d += 0.15 * (node.touches_public_api)                   # 触及公共签名
    d += 0.25 * (history.failure_rate(node.signature_hash)) # 同类节点历史失败率
    return min(1.0, d)
```

### 3.2 预算表

| 难度 | N（3B 采样） | 是否先 plan | 是否 7B 判别 | 节点预算 |
|---|---|---|---|---|
| < 0.3 | 2 | 否 | 否 | ~40 s |
| 0.3–0.6 | 3 | 否 | 否 | ~90 s |
| 0.6–0.8 | 4 | 是（7B 出 3 步计划） | 是（pairwise 选优） | ~180 s |
| > 0.8 | 5 | 是 | 是 + 变异测试 | ~300 s |

`history.failure_rate` 来自任务库的历史统计——**系统跑得越多，算力分配越准**。这就是"agent 设计"相对"裸调模型"最容易被忽视的收益。

## 4. 七个榨干模型的机制

### M1　首稿永不直接交付：强制"自我修复轮"

即使第一个候选通过了闸门，也**强制做一次定向精修**（成本约 +20 s，收益显著）：

```
pass(candidate) →
  修一轮，只允许修这三类问题（由静态检查给出，不让模型自由发挥）：
    ① 未使用的 import / 变量
    ② 圈复杂度 > 10 的函数（要求拆或提前 return）
    ③ 缺失的异常/边界分支（由 checklist 指出，如"参数为 null 时未处理"）
  精修后必须仍全绿，否则回退首稿
```

为什么有效：3B 的"一次通过"往往是**通过但不干净**（能用、冗余、无边界处理）。这一步用最低成本把"能用"推到"可交付"。

### M2　跨模型分工：3B 生成，7B 判别（不是 7B 生成）

关键洞察：**判别比生成容易得多。** 让 7B 从两个候选里挑一个（pairwise），比让它直接写一个，成本低 3–5 倍且更准。

```
候选 A、候选 B（都过了闸门）→ 7B 做三问（JSON 输出，≤400 token）：
  1. 哪个更符合契约？(A/B/平)
  2. 哪个改动面更小、更符合既有风格？(A/B/平)
  3. 有没有闸门没覆盖的隐患？列出最多 2 条
→ 按 1、2 结果选优；若第 3 问有隐患 → 生成一个补充节点（打补丁，不推翻）
```

只在 `difficulty ≥ 0.6` 时启用，避免成本失控。

### M3　测试质量自增强（本项目最关键的质量机制）

**问题的本质**：3B 写的测试是"照着实现写的"——它写什么就测什么，恒真。于是"测试全绿"毫无意义。

四道组合拳：

| 手段 | 做法 | 为什么能治本 |
|---|---|---|
| **先红后绿** | 测试节点先提交失败测试，再由实现节点让其变绿 | 恒真测试在第一步就暴露 |
| **变异测试** | Java=PIT（`pitest-maven`）、Python=mutmut、Node=StrykerJS；对**改动文件**做变异，要求杀死率 ≥60% | 量化"测试到底有没有在验证东西"；3B 生成的测试通常只有 25–40% 杀死率，这一关逼着它补真断言 |
| **属性测试（模板化）** | 从类型签名**自动**生成不变量模板（jqwik / Hypothesis / fast-check），不靠模型想边界 | 边界条件由类型与规约推导，比模型猜准 |
| **负向测试强制** | 每个 public 方法至少 1 个非法输入测试，由模板生成骨架 | 3B 几乎从不主动写异常路径 |

变异测试的工程注意：**首跑很慢**（首次编译变异体），所以按批次跑（每 5–8 节点或每次合并），不按节点跑；并把 PIT 配置写进 `profile.yaml` 的 `commands.mutation`。

### M4　补丁最小性（弱模型在成熟仓库唯一可控的质量手段）

| 度量 | 阈值 | 超限行为 |
|---|---|---|
| diff 行数 | ≤60（MATURE）/ ≤120 | 打回并要求拆分 |
| 改动文件数 | 1（个别 2） | 打回 |
| **无关改动行**（契约未提及且非格式化产生） | 0 | 打回，反馈指出具体行 |
| 新增公共符号 | 0（除非契约要求） | 打回 |

"顺手重构"是 3B 最大恶习，也是最难在 review 里发现的问题。用数字卡死它。

### M5　修复经验库（同一个错不犯第二次）

把每次"失败 → 成功"存成一条经验，下次同类错误自动检索为 few-shot：

```json
{
  "error_sig": "javac:cannot find symbol|setTimeout(int)",
  "context_kind": "java-method-signature-mismatch",
  "bad_patch": "...",
  "good_patch": "...",
  "profile": "spring-vue",
  "count": 7, "success_rate": 0.86
}
```

- 存储：`data/repair_memory.jsonl`
- 检索：复用 prototype 的 BM25 + 向量 + RRF（`src/retrieval/`），按 `error_sig` + 上下文相似度召回 top 2
- 消费：注入 repair prompt 的"历史修复样例"段（**占用历史反馈预算的 ≤400 token**）
- 收益：同类错误的修复通过率随使用次数上升；这是唯一"越用越强"且不需要训练的能力

### M6　候选判别用 checklist 而不是投票

三个候选都过闸门时，不要"少数服从多数"（它们往往差异在细节）。用**结构化 checklist 打分**：

| checklist 项 | 判定 |
|---|---|
| 是否实现了契约的全部要点（逐条 ✅/❌） | 确定性（对比契约） |
| 是否引入新依赖（不应有） | AST 扫描 |
| 是否覆盖异常路径 | 测试存在性 |
| diff 行数最小 | 度量 |
| 是否触碰无关文件 | 度量 |

取 checklist 得分最高者；分相同则取 diff 最小者。**全程不用模型**——判别环节越确定越好。

### M7　反逃避检测（防止模型"作弊式通过"）3B 在压力下会用 5 种方式"让闸门变绿"，必须逐条封堵（`src/gates/anti_cheat.py`）：

| 逃避手法 | 检测 | 处理 |
|---|---|---|
| 改测试让它通过 | 本节点改动集包含测试文件且非 `test` 类节点 | **拒绝**，反馈"不得修改测试来适配实现" |
| 放宽断言（`assertEquals`→`assertNotNull`，`==`→`!= null`） | AST 对比断言强度（比较运算符/期望值变化） | 拒绝 |
| 新增 `@Disabled` / `skip` / `pytest.mark.skip` / `xit` | 正则 + AST | 拒绝 |
| `try { ... } catch (Exception e) { }` 吞异常 | AST：catch 块无 log/rethrow/返回错误 | 拒绝，要求 log 或 rethrow |
| 改构建配置绕过（编译器 target 降级、跳过测试开关、`-DskipTests`） | 检测 `pom.xml`/`build.gradle`/`package.json`/`pytest.ini` 被改 | 拒绝（除非节点是 `config` 且契约明确要求） |
| 注释掉报错代码 / 留 `pass` / 留 `TODO` | 正则 + AST | 拒绝，或标 `NEEDS_HUMAN` |
| 删除既有测试文件 | `git ls-files` 对比 | 拒绝 |

> 这一条是"质量"和"看起来质量"的分界线。没有它，闸门会被系统性绕过，而且**绕过方式会被经验库学走**（M5 反而放大危害）。

---

### M8　计算校验：能实测的绝不推理

3B 最顽固的一类错误是**把断言里的期望值猜错**（实测：`clamp(5,1,3)` 期望写成 `2`，正确是 `3`；
`lo>hi` 的异常用例参数写成合法区间 `(1,0,5)`）。这类错误模型自己永远发现不了——
测试永远红，模型就去改实现凑错误期望，最后只能 `needs_human`。

**规律**：凡是"某一组输入会得到什么结果"这类问题，都是**可实测**的，不需要推理。
把它交给引擎（`core/oracle.py`）：

| 校验项 | 做法 | 产出 |
|---|---|---|
| 正常用例 | 沙箱子进程执行 `func(*args)`，与 `expected` 比值 | 分歧事实：`期望 2 / 实测 3` |
| 异常用例 | 调 `func(*args)` 看是否抛出声明的异常类型 | `期望抛 ValueError / 实测正常返回 1` |
| **自动修 spec** | 在候选参数（反转/交换/±1/通用兜底 ≤10 组）里搜一个真会抛异常的 | `异常用例参数由引擎实测改正为 ['1','5','0']` |
| 字面量合法性 | `args` / `expected` 必须 `literal_eval` 可解析 | 直接拒绝，不渲染坏测试 |

三条使用规则：

1. **分歧不判对错，只给事实**：引擎说"实测返回 3"，但**不**替人决定是实现错还是测试错——把它写进反馈，
   让模型自己选边；两轮后仍有分歧才标 `NEEDS_HUMAN` 并在报告里列出两边。
2. **能算的就别问模型**：反例搜索是 10 次亚秒级调用，比再跑一轮 3B（20 s）便宜得多，且结果确定。
3. **前提是实现已存在**：测试先行阶段 `func` 还不存在，校验返回"无法验算"，不阻塞流程。

> 实测收益：同一个 `clamp` 需求，加 M8 之前反复 `needs_human`；加之后 **12 秒 `done`**，
> 且变异杀死率 2/3（第三个变异体落在异常文案字符串的 `or` 上，属无害存活）。

## 6. 质量分公式与报告

```python
quality = (0.30 * correctness + 0.20 * test_strength + 0.15 * consistency
         + 0.15 * minimality + 0.10 * security  + 0.10 * maintainability)
```

各项归一化到 0–1：

| 项 | 计算 |
|---|---|
| `correctness` | 闸门通过率（加权：构建 0.4 / 测试 0.6） |
| `test_strength` | `0.6 * min(1, 杀死率/0.6) + 0.4 * min(1, 分支覆盖/0.7)` |
| `consistency` | `1 - min(1, 违规数/20)` |
| `minimality` | `1 - min(1, (diff行数-预算)/预算 + 无关改动数*0.2)` |
| `security` | `1 if 命中==0 else 0` |
| `maintainability` | `1 - min(1, 复杂度违规数/10)` |

报告里同时给**分项与总分**，并对比"最近 5 次同类任务的均分"——**质量分应在稳定上升，否则说明引擎改动引入了退化。**

## 7. 成本–收益曲线（什么时候加 N、什么时候升级模型）

| 配置 | 单节点耗时 | 一次通过率（估） | 变异杀死率（估） | 结论 |
|---|---|---|---|---|
| 3B × N=1 | 20 s | 45–55% | 25–35% | 不可交付 |
| 3B × N=3 + 闸门 | 60–90 s | 78–86% | 40–50% | 可用 |
| 3B × N=3 + 闸门 + M1/M7 | 100 s | 85–90% | 45–55% | 推荐默认 |
| 3B × N=3 + 7B 判别（难节点） | 150–200 s | 88–92% | 55–65% | 推荐难节点 |
| 7B × N=2（全量替代） | 180 s | 85–90% | 50–60% | **不推荐**：同质量但慢 2 倍 |
| 3B + M5 经验库（跑过 200 节点后） | 90 s | 90–94% | 55–65% | 长期最优 |

**结论**：在你这个硬件上，"3B + 重验证 + 经验库"是最优解；7B 只用于判别与规划。把人力和时间花在闸门与经验库上，回报率远高于换模型。

## 8. 理论最高质量的边界（诚实表）

| 任务类型 | 3B + 本设计可达 | 说明 |
|---|---|---|
| CRUD + 认证 + 常规业务规则 | **95% 可交付** | 模板 + 契约 + 测试闭环完整 |
| 数据迁移 + 校验逻辑 | 90% | DDL 可执行、迁移可重放 |
| 并发/事务正确性 | **60–70%** | 3B 难以推理竞态；需人工复核 + 专门测试 |
| 算法实现（有明确规格与测试） | 85% | 有测试就收敛很快 |
| 性能优化 | **30%** | 需要度量与经验判断，不适合小模型 |
| 大范围重构（MATURE 仓库） | **20%** | 影响面不可控，本设计选择"拒绝 + 出方案" |
| 安全敏感逻辑（鉴权细粒度/加密） | 65% | 必须人工审查，只做模板化实现 |

**这说明"理论上最高质量"不是 100%**——而是**在每类任务上逼近它的上限，并且诚实地把达不到的部分交给人**。交付报告里必须包含 `NEEDS_HUMAN` 清单，这才是可交付级系统的正确姿态。
