# 10 仓库形态识别与增量开发

> 同一个需求，在"空目录"和"跑了三年的仓库"里，**做法必须完全不同**。
> 本章定义：怎么**用命令客观判定**仓库处于什么阶段，以及每种阶段下 Agent 的策略差异。

---

## 1. 探测信号（全部来自 git 与文件系统，不靠模型猜）

`src/repo/probe.py` 输出的原始信号：

| 信号 | 获取方式 | 用途 |
|---|---|---|
| `is_repo` | `git rev-parse --is-inside-work-tree` | 是否 git 仓库 |
| `commit_count` | `git rev-list --count HEAD` | 有无历史；规模 |
| `first_commit_days` | `git log --reverse --format=%ct \| head -1` | 项目年龄 |
| `last_commit_days` | `git log -1 --format=%ct` | 是否活跃 |
| `author_count` | `git shortlog -sne \| wc -l` | 单人玩具 / 团队项目 |
| `dirty_files` | `git status --porcelain` | 工作区是否干净（安全前提） |
| `current_branch` / `ahead_behind` | `git status -sb` | 是否在特性分支 |
| `tracked_file_count` | `git ls-files \| wc -l` | 规模 |
| `lang_composition` | 按扩展名统计 + 权重（排除 vendor/lock/生成物） | 主语言判定 |
| `has_src` | 是否存在 `src/` `app/` `lib/` `pkg/` 且含源码 | 是否只是脚手架 |
| `has_tests` / `test_file_count` | 匹配 `test_*.py` `*Test.java` `*.spec.ts` 等 | 测试地基 |
| `tests_green` | 跑一次 profile 的 test 命令（只读，不产出） | **最关键**：基线是否可信 |
| `has_build` / `builds` | 试跑 build 命令（超时 90 s） | 能否构建 |
| `has_ci` | `.github/workflows/` `.gitlab-ci.yml` `Jenkinsfile` | 工程成熟度 |
| `has_migrations` | `db/migration/` `migrations/` `alembic/` `flyway.conf` | 数据层成熟度 |
| `has_lockfile` | `package-lock.json` `pom.xml` `poetry.lock` `requirements.txt` | 依赖可复现 |
| `profile_match` | 现有结构 → profile 特征匹配度（0–1） | 是否已有技术栈 |
| `taken_over` | 存在 `.sixcoder/` | 是否已被本工具接管过 |
| `conventions_signal` | 缩进/命名/包结构采样（200 文件抽样） | 增量开发时的风格来源 |

> 所有探测命令统一走 `src/toolchain/exec.py`（见 11），保证注入正确的 JDK/Node/Python 环境，且**只读**：探测阶段绝不写文件、绝不 commit。

## 2. 形态判定（决策树，确定性）

```python
def classify(s) -> RepoState:
    if not s.is_repo and s.tracked_file_count == 0:
        return GREENFIELD                     # 空目录 / 只有 .git 无提交
    if s.commit_count == 0 or s.tracked_file_count == 0:
        return GREENFIELD
    if not s.has_src and s.tracked_file_count < 15:
        return SCAFFOLDED                     # 只有 README/配置/脚手架
    baseline_ok = s.builds and s.tests_green
    if not baseline_ok:
        return BROKEN_BASELINE                # ★ 宁可先修地基，也不在流沙上盖楼
    if s.has_tests and s.has_ci and s.has_migrations and s.author_count >= 2:
        return MATURE
    if s.has_tests:
        return GROWING
    return YOUNG                              # 有源码无测试
```

| 状态 | 判定要点 | 一句话策略 |
|---|---|---|
| `GREENFIELD` | 空 / 无提交 | 契约先行 + 模板全量生成 |
| `SCAFFOLDED` | 有提交但几乎无源码 | 复用骨架，只插节点 |
| `BROKEN_BASELINE` | 构建不过 或 测试不绿 | **先建立可验证基线**，功能需求后置 |
| `YOUNG` | 有源码、无测试 | 先补测试地基（对已有代码补特征测试），再开发 |
| `GROWING` | 源码 + 测试 | 正常增量，最小补丁 |
| `MATURE` | + CI + 迁移 + 多人 | 强约束增量：全量回归 + 风格继承 + 影响面分析 |

### 2.1 为什么 `BROKEN_BASELINE` 要独立成一态

**在构建不过或测试不绿的仓库上做增量开发，是本项目最容易产生的灾难**：你无法区分"我这次改坏了"和"它本来就坏"。3B 拿到一个失败测试，会去修那个与本次需求毫不相关的历史 bug，越改越乱。

处理流程固定：

```
BROKEN_BASELINE →
  ① 生成"基线修复报告"（哪些测试失败、哪些是环境问题 vs 代码问题）
  ② 只做一件事：把基线修绿（或把不可修的测试隔离并记录 `@Disabled 原因`）
  ③ 人工确认基线置信度（"这些测试可信" / "这些测试已过时"）
  ④ 重新探测 → 状态升级为 YOUNG/GROWING → 才开始真正的需求
```

这一步是硬闸门，用户可以显式跳过（`--force-on-broken-baseline`），但报告里会永久记录"本次交付的基线不可信"。

## 3. 各形态下的策略差异（核心表）

| 维度 | GREENFIELD | YOUNG / GROWING | MATURE |
|---|---|---|---|
| 上下文主要来源 | **契约 + 模板**（模板占 70%） | 模板 40% + 检索 60% | **检索 + 符号索引**（新代码 ≤20%） |
| 上下文预算分配 | 契约 1000 / 模板 1500 / 规约 800 | 均衡 | 目标代码 1500 / 邻居 1200 / 规约 400 / 契约 400 |
| 节点展开 | 从需求全量展开 | 部分展开 + 插入 | **只插入叶子节点**，禁止改骨架 |
| 实现自由度 | 中（模板约束） | 中 | **低**（必须复用既有抽象与命名） |
| 必过闸门 | G1–G5 + D1–D8 | + **全量测试回归** | + 全量回归 + 依赖方向检查 + 覆盖率不得下降 |
| 风格来源 | `profile.conventions.md` | 混合：既有代码采样 + profile | **从既有代码反推**（覆盖 profile 默认） |
| 查重（避免重复造轮子） | 不需要 | **必须**：先 `code_search` 找同义实现 | **强制**：命中即改为"复用/扩展"而非新建 |
| 影响面分析 | 不需要 | 1 跳 | **2 跳 + 公开 API 兼容性检查** |
| 补丁预算 | ≤120 行/节点 | ≤100 行 | **≤60 行/节点**，超出必须拆分 |
| 拒绝条件 | 无 | — | 需改 ≥3 个公共签名 / 需跨模块重构 → **拒绝并出方案文档** |

> MATURE 那一列的"拒绝"很重要：3B 在成熟仓库里做大范围重构的失败率接近 100%，且破坏面不可控。**诚实地拒绝并给出人工方案文档，比假装做了更有价值。**

## 4. 增量开发的四步固定动作

在任何"已有代码"的仓库里，节点执行前必须先做这四步（`src/repo/impact.py`）：

### 步骤 1：查重（防止重复实现）

```
code_search(契约中的核心名词 + 同义词) → top 8
   ├── 命中且语义相符 → 节点改为 "extend/<symbol>"：只加参数/分支
   ├── 命中但不同用途 → 记录到上下文③（告知模型"已有相似实现，命名请区分"）
   └── 无命中 → 正常新建
```

3B 最爱干的事是"重新写一个 `UserService`"而不是扩展已有的。查重是**确定性的**，不能靠模型自觉。

### 步骤 2：影响面分析（1–2 跳）

```
目标符号 → 被谁调用（callers）→ 那些调用者的契约是否受签名变更影响
        → 被谁实现（implements/overrides）→ 实现方是否要同步改
```

- **1 跳**：函数/方法级改动
- **2 跳**：接口/公开 API 改动（必须检查所有实现与外部调用）
- 影响面节点自动加入任务图，**作为依赖前置**（先改调用方？不——先改接口，再批量改实现，最后一跳改调用方，顺序由依赖图决定）

### 步骤 3：最小补丁

| 约束 | 值 | 判定 |
|---|---|---|
| diff 行数 | ≤ 60（MATURE）/ ≤120（其他） | `git diff --numstat` |
| 改动文件数 | 1（个别节点 ≤2） | — |
| 无关改动 | 0 | 模型输出的 SEARCH 块若包含契约未提及的行 → 打回 |
| 新增公共符号 | 0（除非契约要求） | AST 对比 |

"补丁最小性"是弱模型在成熟仓库里唯一可控的质量手段。

### 步骤 4：全量回归

MATURE/YOUNG 状态**不跑全量测试不算完成**。为控制时间：

- 节点级：跑本节点绑定测试（G5）
- 批次级（每 5–8 节点或每次合并）：跑全量 + 覆盖率对比，**覆盖率不得下降**

## 5. 与任务图的关系

| 形态 | 任务图构造方式 |
|---|---|
| GREENFIELD | 从需求**全量展开**（07 §2 的规则） |
| SCAFFOLDED | 从现有骨架**映射**：已存在的文件不重建，只在其上展开叶子节点 |
| YOUNG/GROWING/MATURE | **插入式**：需求 → 查重 → 影响面 → 生成最小节点集，挂到既有代码的符号图上 |

插入式任务图多两类节点：

- `baseline`（仅 BROKEN_BASELINE / YOUNG）：补特征测试、修环境
- `impact`（仅 MATURE）：影响面同步改动

## 6. 脏工作区与安全

| 情况 | 行为 |
|---|---|
| `dirty_files` 非空 | **拒绝启动**，提示：`检测到 12 个未提交改动。请先 git stash / commit，或选择"仅生成补丁不落盘"模式` |
| 在非 default 分支 | 提示，允许继续（本工具在自己的快照分支上工作） |
| 仓库远端有未拉取提交 | 提示（避免基于旧代码开发） |
| 本工具接管过（有 `.sixcoder/`） | 复用上次的 `CONVENTIONS.md` 与符号索引，节点可增量（省 30% 时间） |

**隔离方式**：所有改动都在 `workspaces/<task_id>/` 的**克隆副本**里做，用户仓库零风险；交付时给 patch 或让用户 `git pull` 该副本的分支。
