# 11 技术栈选型、工具链配置与帮助系统

> 三件事：**自动选对技术栈**、**让编译器/构建工具能找到（可配置目录）**、**出了问题能自助解决**。
> 共同原则：**一切探测都是命令 + 解析，绝不靠模型猜；一切失败都给可执行的修复动作。**

---

## 1. 技术栈自动选型

### 1.1 输入与约束

```
需求文本
本机环境快照（哪些工具链可用、版本多少）   ← 硬约束，优先于偏好
历史偏好（settings.yaml 里的 team_defaults）
若为增量仓库：现有语言构成 + profile_match
```

**硬约束优先**：需求命中 `spring-vue` 能力，但本机没有 JDK 17 → **不推荐**该方案（推荐一个能在此机器上真正跑起来的方案），同时给出"装 JDK 后可解锁该方案"的提示。

### 1.2 打分算法（`src/profiles/select.py`，确定性 + 可解释）

```python
def select(requirement, env, repo, settings) -> StackDecision:
    scores = {}
    for p in load_profiles():
        cap_hit   = len(capabilities_of(requirement) & p.capabilities)      # 能力命中数
        cap_miss  = len(capabilities_of(requirement) - p.capabilities)      # 不支持数
        env_ok    = p.toolchains_available(env)                             # 工具链可用性 0/1
        repo_fit  = repo.profile_match.get(p.id, 0) if repo.is_incremental else 0.5
        pref      = settings.team_defaults.get(p.id, 0)
        scale     = 1.0 if estimate_nodes(requirement) <= p.limits.max_nodes else 0.0

        scores[p.id] = (
            3.0 * cap_hit
          - 5.0 * cap_miss                 # 不支持的能力重罚
          + 2.0 * repo_fit                 # 增量仓库强烈倾向同栈
          + 1.0 * pref
          + 1.5 * env_ok                   # 环境不可用直接掉队
        ) * scale
    return explain(scores)                 # 可解释：给出 top1 + 为什么不是 top2
```

**输出必须是可解释的三段**：

```
推荐：python-fastapi（得分 8.4）
理由：需求中的 3 项能力（crud-api / jwt-auth / file-upload）全部命中；
      本机 Python 3.12 + uvicorn 已就绪；
      该仓库现有 62% 的代码是 Python（增量开发强烈倾向同栈）。
不选 spring-vue（得分 2.1）：需求 3 项能力同样命中，但本机未检测到 JDK 17
      （详见设置 → 工具链 → Java）；且现有仓库是 Python 项目，混栈会引入双运行时。
不选 node-cli（得分 -1.6）：缺少 file-upload、jwt-auth 能力。
```

用户可一键覆盖（下拉框），覆盖后**记入 `settings.team_defaults` 权重**，下次更准。

### 1.3 语言判定不是"问模型"

需求里写"做一个图书管理系统"，模型**不该**被问"用 Java 还是 Python"——这是环境与惯例问题，不是语义问题。
模型只在一种情况下参与：需求里出现了明确的**技术线索**（"用 FastAPI 写"、"要部署到 K8s"），此时用 1.5B 做一次**关键词抽取**（0 推理成本的规则优先，规则不中才调模型），把线索加入打分。

## 2. 工具链配置（设置里指定目录）

### 2.1 设计目标

| 目标 | 做法 |
|---|---|
| 用户能指定 JDK 装在哪 | 设置页每项可"指定目录"，落 `toolchains.yaml` |
| 不依赖用户全局环境变量 | 每次执行都**显式注入**环境（JAVA_HOME/PATH 等），不读全局 |
| 找不到时能自助解决 | 自动探测 + 安装命令 + 官方下载链接（见 §3 帮助） |
| 版本必须校验 | 解析 `java -version` 等输出，不满足 `version_req` 即报"版本不符"而非"可用" |
| 结果可缓存、可失效 | 缓存 24 h 或工具链文件 mtime 变化时重探 |

### 2.2 `toolchains.yaml`（用户级，`%APPDATA%\SixAgent\toolchains.yaml`，**不入仓库**）

```yaml
# 只写"覆盖项"，未写的走自动探测。路径可以是目录或可执行文件。
java:
  home: "C:/Program Files/Eclipse Adoptium/jdk-17.0.13.11-hotspot"
  # 或 java:  { exe: "D:/jdk17/bin/java.exe" }
maven:
  exe: "D:/apache-maven-3.9.9/bin/mvn.cmd"
  # home 亦可；settings 会自动推导 M2_HOME 并注入
node:
  home: "C:/Program Files/nodejs"     # 必须 >= 20
python:
  exe: "D:/Python/python.exe"         # 本项目自身用 3.12；目标项目可另指
docker:
  exe: "C:/Program Files/Docker/Docker/resources/bin/docker.exe"
  compose: "docker compose"           # 或 docker-compose
git:
  exe: ""                             # 空 = 用 PATH
```

### 2.3 每个工具链的声明（`profile.yaml` 里声明需求，`src/toolchain/registry.py` 里实现探测）

```python
Toolchain(
    id="java",
    version_req=">=17",                       # 16 也报错，因为 profile 要求 17
    probe_cmd=[("java", "-version")],
    version_regex=r'version "(\d+)',
    discover=[
        "settings:java.home",                 # ① 用户设置（最高优先）
        "env:JAVA_HOME",                      # ② 环境变量
        "path:java",                          # ③ PATH
        "dirs:",                              # ④ 常见安装目录 glob
        "C:/Program Files/Eclipse Adoptium/*",
        "C:/Program Files/Java/*",
        "D:/Java/*", "D:/jdk*",
    ],
    env_when_used={"JAVA_HOME": "{home}", "PATH": "{home}/bin;{PATH}"},
)
```

探测顺序 **设置 > 环境变量 > PATH > 常见目录**，命中即停；全部失败 → 状态 `MISSING`，附带 `fix`（§3 帮助条目 id）。

### 2.4 统一的命令执行封装（所有闸门和工具都用它）

```python
# src/toolchain/exec.py
def run(cmd, cwd, toolchains, timeout=180) -> CmdResult:
    env = os.environ.copy()
    for tc in toolchains.required_for(cmd):          # 例如 mvn 需要 java
        env.update(tc.render_env())                  # 注入 JAVA_HOME / PATH
    p = subprocess.run(cmd, cwd=cwd, env=env, capture_output=True,
                       timeout=timeout, shell=isinstance(cmd, str))
    return CmdResult(code=p.returncode, out=p.stdout, err=p.stderr)
```

**为什么必须显式注入**：Windows 上用户机器常有多个 JDK，全局 `JAVA_HOME` 指向 8、项目要 17。不注入就必然出现"编译能过但运行报 UnsupportedClassVersionError"这种极难排查的问题。

## 3. 帮助系统（"最好给个帮助"）

### 3.1 设计要点：帮助必须**与代码同源、可测试、能被模型消费**

帮助不是一堆静态文字，而是一张结构化表 `src/help/entries.yaml`：

```yaml
- id: toolchain.java.missing
  title: 未检测到 JDK 17
  severity: blocking
  detect: "toolchain:java"                 # 对应探测函数，状态 MISSING 时命中
  body: |
    Java 版 SixAgent 的 profile 需要 JDK 17 或更高。
    JDK 与 JRE 不同：JRE 只能运行，无法编译，请安装 JDK。
  fix_actions:
    - label: "用 winget 安装（推荐）"
      cmd: "winget install EclipseAdoptium.Temurin.17.JDK"
      verify: ["java", "-version"]
    - label: "手动下载"
      url: "https://adoptium.net/temurin/releases/?version=17"
    - label: "我已经装好了，去设置里指定"
      nav: settings/toolchains/java
  help_links: ["https://adoptium.net/installation/"]
```

三个消费方共用同一份数据：

1. **设置页 / 首次向导**：渲染 `[怎么装?]`
2. **闸门失败时**：把匹配条目的 `fix_actions` 注入到 repair 反馈（见下）
3. **CLI**：`python -m src.doctor` 输出全部命中项

### 3.2 错误即帮助：把修复动作送进 Agent 的循环

这是本项目的一个巧妙之处——**帮助条目直接提升模型的一次通过率**：

闸门失败 → `feedback.py` 组装反馈时，先按错误特征匹配 help entry：

```
【失败闸门】G2 构建
【错误】javac: invalid target release: 21   ——  该错误匹配帮助条目 toolchain.java.version_mismatch
【环境】检测到 JAVA_HOME=C:\jdk8（工具链 java 实际使用 1.8.0_392）
【可用修复】该错误通常由 JDK 版本不符引起。可选动作：
   1) 设置 → 工具链 → Java 指定 JDK 17 目录
   2) winget install EclipseAdoptium.Temurin.17.JDK
【提示】不要修改 build.gradle 的 target 版本，需求未要求变更编译目标。
```

注意最后一行：**明确禁止模型用"改配置绕过"的方式"修复"环境问题**——这是 3B 的经典逃避路径（把 `maven.compiler.target` 从 17 改成 8 让它编译过）。

### 3.3 首次运行向导（3 步，每步可跳过）

```
[1/3] 选择模型       自动列出 ollama list 的结果，推荐 qwen2.5-coder:3b（本机 4GB 显存）
                     检测：模型存在？显存够装？显示实测 tok/s
[2/3] 工具链体检     列出检测结果；阻塞项必须处理（带安装命令），非阻塞项可跳过
[3/3] 选择技术栈     profile 列表 + 本机可用性 + 推荐项（11 §1.2 的算法）；可设为默认
```

完成后写 `settings.yaml`（模型档位 / 默认 profile / 工具链覆盖），并在帮助中心记录"你的环境已完成 X 项检查，Y 项建议处理"。

### 3.4 帮助中心（`HelpView.vue`）

| 分组 | 内容 |
|---|---|
| 快速开始 | 三条命令跑通第一个需求 |
| 工具链 | 每个工具链的"怎么装 / 怎么指定目录 / 常见坑"（JDK vs JRE、多版本冲突、公司代理） |
| 模型 | 4GB 显存下为什么选 3B、怎么加 7B、速度实测、显存溢出症状 |
| 不理解的行为 | "为什么它拒绝了我的需求"（能力求交）、"为什么它先修测试不修功能"（BROKEN_BASELINE）、"为什么它只改了 40 行"（补丁预算） |
| 故障排查 | 走 09 §6 的表 |
| 关于交付级别 | 08 §M4 的 8 条门禁解释，明确"什么算交付" |

### 3.5 帮助的可测试性（防止腐化）

| 规则 | 校验 |
|---|---|
| 每个 `fix_actions` 里的命令必须**存在对应可执行文件** | `pytest tests/help/test_entries.py` 逐条 `shutil.which()` |
| 每个 `detect` 必须有单测 | 每条帮助条目至少 1 个用例 |
| 每个 `nav` 目标必须在路由中存在 | 前端构建期校验 |
| 帮助里提到的设置项必须在 `settings.schema.json` 中存在 | 同上 |

> 帮助文档腐化是软件工业的常态。**把帮助做成代码（可断言、可测试），它才不会烂。**
